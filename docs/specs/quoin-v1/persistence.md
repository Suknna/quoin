# Quoin v1 — 数据与事务规格（persistence.md）

**状态：Draft**

**CATEGORY 前缀：`DATA`**（SPEC-TRACE-002）

**Non-normative：** 本文件是 Quoin v1 的 SQLite 数据模型、聚合关系、唯一约束、事务程序、迁移、Artifact 与派生索引的规范性说明。机器可表达的表、列、索引、外键、CHECK 与触发器只由 [`contracts/sql/schema.sql`](contracts/sql/schema.sql) 承载；本文件解释其语义、跨聚合事务、生命周期与迁移约束，**不复制完整字段清单**（SPEC-AUTHORITY-002）。规范条款来源为 [`CONTEXT.md`](../../../CONTEXT.md) 稳定标题、[Issue #9](https://github.com/Suknna/quoin/issues/9)（Q9.1 A / Q9.2 A）、[Issue #8](https://github.com/Suknna/quoin/issues/8)、[Issue #2](https://github.com/Suknna/quoin/issues/2)、[Issue #20](https://github.com/Suknna/quoin/issues/20)、[Issue #13](https://github.com/Suknna/quoin/issues/13) 及证据 commit（`prototype/issue-20-sqlite-persistence@582042e4d2bb740ff6a1b9feab94875e7c5360ff`、`research/sqlite-capabilities@2cfb8841d9798bd27114e44b4576f2f1ad1a4ea7`）。

## 1. 范围与权威

- **DATA-SCOPE-001 —** `contracts/sql/schema.sql` **MUST** 是 Quoin v1 当前完整 SQLite Schema 的唯一机器权威；本文件 **MUST NOT** 复制其表/列/约束清单，引用时 **MUST** 使用相对路径与稳定 symbol（表名、约束名、索引名）。（来源：Issue #8「机器契约目录」）
- **DATA-SCOPE-002 —** 以下事实在 v1 **MUST NOT** 持久化到 SQLite，并由本文件明确解释其归属：Journey Catalog **内容**只作为构建产物嵌入 Quoin/Lintel；配置版本与 Browser Identity Revision 仅保存创建时校验 provenance，每个 `browser_operations` 保存实际执行 binding，Run/Test Run 不复制 binding；Stele 告警源凭据只读快照仅内存缓存（`alert_deliveries` 只保存非秘密 `credential_id` 与快照版本）；Kubernetes 运行时状态由人工调查按需只读查询，不建表；Execution Attempt 工作区与 Browser profile 本体在各自卷/目录，不进入 SQLite 备份；未查看通知的 toast 是内存态，服务端只持久化 `user_viewed` 投影。（来源：CONTEXT「Journey Catalog」「服务身份」「Kubernetes 运行时状态」「浏览器身份」「后台任务提示」）
- **DATA-SCOPE-003 —** 派生投影（`knowledge_search_docs`、`knowledge_fts`、`embeddings`、`alert_change_log`、`task_change_log`、`user_viewed`）**MUST** 可丢弃、可重建，**MUST NOT** 成为对应领域事实的第二权威源。（来源：CONTEXT「可复用知识」「实时投影」「调查与巡检工作区」「后台任务提示」）

## 2. 账号与会话

- **DATA-AUTH-001 —** `users` **MUST** 持久化 `password_change_required` 与 `password_change_required_at`：离线创建首个 Admin、Admin 离线重置密码与备份恢复流程 **MUST** 在同一事务置位（`password_change_required=1` 时必须有置位时间戳，CHECK 强制）；成功改密 **MUST** 在同一事务清除标志；清除标志 **MUST NOT** 由其他业务命令隐式完成。（来源：CONTEXT「本地账号认证」「管理员离线恢复」「一致备份」）
- **DATA-AUTH-002 —** `password_change_required=1` 的用户登录后 **MUST** 只获得受限 Session：**MUST** 只能调用自身状态读取、改密与登出；权限层 **MUST** 以该持久状态裁决，**MUST NOT** 依赖前端隐藏入口。（来源：CONTEXT「本地账号认证」「管理员离线恢复」）
- **DATA-AUTH-003 —** `sessions` **MUST** 只保存 raw 32-byte bearer 的固定长度 SHA-256 digest（`session_token_digest`，UNIQUE、BLOB 32 字节）；raw bearer **MUST** 只存在于浏览器 Cookie 与认证瞬间内存，**MUST NOT** 写入 SQLite、日志或审计。（来源：CONTEXT「同源 Web 会话」「模型调用边界」）
- **DATA-AUTH-004 —** `users.row_version` **MUST** 从 1 起始、与 `auth_revision` 相互独立，任何允许的 UPDATE **MUST** 恰好递增 1（`trg_users_row_version_increment`）；`updateUser`/`resetUserPassword` 等修改用户状态的命令 **MUST** 携带 `expected_row_version` 并在同一 UPDATE 的 WHERE 中比较（DATA-COMMAND-005）；`auth_revision` 仍由账号变更事务按既有规则递增并撤销 Session，两者 **MUST NOT** 混用（HTTP-COMMAND-002）。（来源：CONTEXT「本地账号认证」）
- **DATA-AUTH-005 —** Session 创建 **MUST** 绑定同一 enabled User 的当前 `auth_revision`（`trg_sessions_insert_current_auth_revision`）；`user_id/session_token_digest/auth_revision_at_issue/created_at` 创建后不可改写。账号安全字段（enabled、role、password PHC、强制改密状态）变化 **MUST** 恰好推进一次 `auth_revision`，无安全字段变化不得空推进。Admin 重置密码事务 **MUST** 先把该用户全部有效 Session 置为 revoked 并在同一事务更新密码、强制改密状态、`auth_revision` 与 `row_version`；即使连接在提交前已读到旧 bearer，后续受保护入口也因 `auth_revision_at_issue != users.auth_revision` 拒绝。（来源：CONTEXT「本地账号认证」、HTTP-AUTH-003）

## 3. 技术 locator 与身份规则

- **DATA-IDENT-001 —** Quoin 生成、且没有用户稳定 key 的记录 **MUST** 使用正 64-bit SQLite INTEGER locator（`INTEGER PRIMARY KEY CHECK (id > 0)`）。需要保证已分配 ID 永不复用的领域 locator 与单调序列（如 `alert_change_log.id`）**MUST** 使用 `AUTOINCREMENT`；单行表（`schema_state`、`backup_settings`）与纯投影/连接表 **MAY** 使用普通 `INTEGER PRIMARY KEY`（Q9.1 A）。（来源：[Issue #9](https://github.com/Suknna/quoin/issues/9) Q9.1）
- **DATA-IDENT-002 —** locator 的 HTTP 十进制字符串表示与 Proto `int64` 表示 **MUST** 由 `http-api.md`（#10）与 `runtime-protocol.md`（#11）定义；本文件只定义存储形态为 INTEGER。（来源：[Issue #9](https://github.com/Suknna/quoin/issues/9) Q9.1）
- **DATA-IDENT-003 —** 用户稳定 key（`business_systems.key`、`alert_sources.source_key`、`connections.name`、`config_discoveries.discovery_key`、`config_plans.plan_key`、`config_checks.check_key`、`runtime_slots.slot` 固定两行）以及复合领域身份（`alert_occurrences` 三元组、`observed_resources` 三元组）**MUST** 是相等性权威且不可改写（schema 触发器冻结）；locator **MUST NOT** 参与领域去重或业务相等判断，**MUST NOT** 以隐藏 UUID 替代稳定身份。（来源：CONTEXT「稳定身份保留」「服务身份」）
- **DATA-IDENT-004 —** ID 允许间隙，**MUST NOT** 被解释为业务时间或提交顺序；顺序 **MUST** 只由显式序列承载（`alert_change_log.id`、`investigation_messages.seq`、`model_calls.call_seq` 等）。（来源：CONTEXT「实时投影」「撤回消息」）
- **DATA-IDENT-005 —** 已发布、已执行 Test Run 或被历史引用的稳定 key **MUST** 以 tombstone（Disabled/Retired）保留，**MUST NOT** 释放给新对象；仅从未发布、从未运行且从未被引用的草稿/staging 可在 DATA-TX-015 程序下物理清理。（来源：CONTEXT「稳定身份保留」）
- **DATA-IDENT-006 —** Alertmanager fingerprint **MUST** 保存为上游 64-bit 无符号值的 8 字节大端 BLOB（`alert_occurrences.fingerprint`、`alert_delivery_items.fingerprint`，CHECK `length = 8`）；**MUST NOT** 使用有符号整数或 SHA-256 替代。（来源：CONTEXT「告警发生」、Issue #9）
- **DATA-IDENT-007 —** `starts_at` **MUST** 无损规范化为 UTC RFC3339Nano 文本并参与 Occurrence 身份；规范化 **MUST NOT** 截断时间精度，**MUST NOT** 因时区/亚秒差异拆分同一告警。（来源：CONTEXT「告警发生」）

## 4. 领域写命令与并发前提

- **DATA-COMMAND-001 —** 所有经认证外部调用者发起的领域写命令 **MUST** 以 `(principal_type, principal_id, client_command_id)` 唯一（`client_commands` UNIQUE），保存命令类型、非秘密请求摘要、确定性结果与结果对象引用。（来源：CONTEXT「领域写命令契约」）
- **DATA-COMMAND-002 —** 请求摘要 **MUST** 覆盖全部语义请求字段，**包括** `expected_row_version`、`expected_head_message_id` 等并发前提；重试携带与原请求相同的摘要。摘要 **MUST NOT** 包含 nonce、时间戳或其他不影响语义的字段。（来源：CONTEXT「领域写命令契约」、Issue #9 Q9.1 确认；Rationale：若摘要排除 `expected_*`，版本前提不同的两个写请求会被误判为同一命令。）
- **DATA-COMMAND-003 —** 相同 ID 且相同摘要重放 **MUST** 返回原确定性结果（`result_payload_json`）；相同 ID 但不同摘要 **MUST** 返回冲突，**MUST NOT** 静默以新请求执行。（来源：CONTEXT「领域写命令契约」）
- **DATA-COMMAND-004 —** 确定性业务拒绝（版本冲突、fence 拒绝、校验失败）**MUST** 以 `outcome='rejected_known'` 持久化结果；基础设施失败或提交结果未知 **MUST NOT** 被伪造为权威成功或失败，调用方 **MUST** 复用同一 `client_command_id` 重试。（来源：CONTEXT「领域写命令契约」）
- **DATA-COMMAND-005 —** 修改当前状态或当前版本指针的命令 **MUST** 携带 `expected_row_version` 并在同一 UPDATE 的 WHERE 中比较；纯追加创建 **MUST NOT** 强制 expected version。（来源：CONTEXT「领域写命令契约」）
- **DATA-COMMAND-006 —** 调度器创建定时 Run **MUST** 使用 `(business_system_id, plan_key, scheduled_for)` 确定性键（`ux_inspection_run_scheduled` 部分唯一索引），该键在 Run 进入任何终态后仍 **MUST NOT** 被复用（不补跑）；同一事务 **MUST** 绑定当时生效的 `config_version_id` 与 `label_contract_version_id`。（来源：CONTEXT「领域写命令契约」「巡检运行」）
- **DATA-COMMAND-008 —** 语义 no-op（请求字段存在但值未变化）**MUST** 幂等成功返回当前对象：**MUST NOT** 执行 UPDATE、递增 `row_version`、产生 SSE 变更事件或重复写成功审计；命令账本仍记录并重放确定性结果（DATA-COMMAND-003/004）。（来源：Issue #10 复审）
- **DATA-ROWVER-001 —** 每个可变聚合根 **MUST** 持久化独立 `row_version`（从 1 起始，CHECK `>= 1`）并配恰好递增 1 的 BEFORE UPDATE 触发器（`WHEN NEW.row_version <> OLD.row_version + 1` 时 RAISE）：`users`（与 `auth_revision` 独立）、`runtime_slots`、`alert_sources`、`alert_source_credentials`、`alert_occurrences`、`alert_intake_issues`、`initial_analyses`、`browser_identities`、`browser_operations`、`inspection_runs`、`execution_attempts`、`tool_calls`、`label_contracts`、`label_contract_state`、`business_systems`、`connections`、`business_system_kubernetes_connections`、`reusable_knowledge`、`knowledge_version_retrieval_state`、`knowledge_import_batches`、`knowledge_candidates`、`backup_settings`、`runtime_credentials`、`runtime_artifact_uploads`（触发器名 `trg_<table>_row_version_increment`）；应用在同一条 UPDATE 的 WHERE/SET 中比较并递增 `row_version`（SQLite 触发器无法 SET NEW），触发器验证恰好 +1；`alert_change_log`/`task_change_log` 的 `row_version` 列是事件载荷（记录事件时对象版本），日志本身不可变，**MUST NOT** 适用本规则。修改状态/current 指针的命令 **MUST** 携带 `expected_row_version` 并在同一 UPDATE 的 WHERE 中比较（DATA-COMMAND-005），陈旧值命中 0 行由应用映射 409；纯追加创建 **MUST NOT** 强制 expected version。（来源：CONTEXT「领域写命令契约」）

## 5. 审计与执行溯源

- **DATA-AUDIT-001 —** `audit_events` / `audit_event_targets` **MUST** 追加且不可改写（触发器禁止 UPDATE/DELETE），记录 actor、action、target（类型/ID/版本）、命令 ID、提交时间、结果与领域记录引用。（来源：CONTEXT「审计与执行溯源」）
- **DATA-AUDIT-002 —** 审计 **MUST NOT** 复制消息、Evidence、附件、Prompt 正文或秘密；隐藏思维链 **MUST NOT** 被存储或展示。（来源：CONTEXT「审计与执行溯源」「模型调用边界」）
- **DATA-AUDIT-003 —** 每个 `execution_attempts` **MUST** 保存 Agent 与 Quoin Release 版本，并通过不可变 `attempt_input_snapshots`/`attempt_input_items` 保存输入 schema、Prompt renderer 版本、来源、顺序、源 digest 与总 digest；**MUST NOT** 复制来源正文。每个物理 `model_calls` **MUST** 另保存 Tool Schema 版本/digest、逻辑 call/retry 序号、真实 `attempt_connection_grants`、模型 ID、瞬态输入来源 digest、实际规范 provider 请求 digest、淘汰回合数、usage、延迟、provider request ID 与结构化终止原因；同 `call_seq` 的自动物理重试只允许前一行无任何 output 且原因属于 `timeout|rate_limited|transport_error`，或无 output 的 `context_overflow` 且下一行增加淘汰回合；`provider_unavailable`、取消/终态 fence、invalid response 与 artifact commit failure 不得自动重试。`model_call_input_items` 保存本次模型实际看见的来源谱系，`model_call_outputs` 保存规范化完整或部分 provider 响应及 digest，隐藏思维链除外。每个 `tool_calls` **MUST** 保存所属 Model Call、provider tool-call ID/ordinal、参数、执行模式、结果位置与错误；v1 不在 supervisor 内部自动重试 Tool，模型再次请求必须形成新的 Model Call 与 Tool Call；结果正文由 inline JSON 或现有 Artifact store 承担。`model_calls`/`tool_calls` 的物理尝试与终态 **MUST** 不可改写或删除。（来源：CONTEXT「审计与执行溯源」「执行尝试」、Issue #13）
- **DATA-AUDIT-004 —** 确定性业务拒绝 **MUST** 以零领域状态变更的短事务同时提交命令 outcome 与审计事件；提交结果未知的基础设施失败 **MUST NOT** 写入权威失败审计。（来源：CONTEXT「领域写命令契约」「审计与执行溯源」）

## 6. 告警接入与生命周期

- **DATA-ALERT-001 —** `alert_deliveries.body` **MUST** 以 BLOB 直接存 SQLite（不存 Artifact）以维持接入单事务语义与精确原始字节（可能非 UTF-8），`body_size_bytes` 以字节计并由 CHECK 与 BLOB 长度一致；`relay_id` **MUST** 唯一（重试幂等）。整体 JSON 或 `alerts[]` 无法可靠枚举时记录 `status='rejected'` 且 **MUST NOT** 更新任何 Occurrence。（来源：CONTEXT「告警送达」「产物」）
- **DATA-ALERT-002 —** 顶层可解析时 **MUST** 在同一 SQLite 事务中预检全部 `alert_delivery_items`：正常项更新 Occurrence/Observation，`identity_conflict`/`fingerprint_mismatch` 项进入 `alert_intake_issues`；数组第一项 **MUST NOT** 因先处理而获胜，异常项 **MUST NOT** 阻塞正常项。（来源：CONTEXT「告警送达」「告警接入问题」）
- **DATA-ALERT-003 —** `truncatedAlerts > 0` 时 **MUST** 正常处理已包含项、以 `kind='delivery_truncated'` 永久标记 Delivery 与来源，commit 后返回 204；**MUST NOT** 对未知缺失项作任何生命周期推断。（来源：CONTEXT「告警送达」）
- **DATA-ALERT-004 —** Occurrence 身份 **MUST** 为 `(source_id, fingerprint, starts_at)` 唯一三元组；不可变完整 labels 快照（`labels_canonical` + `labels_digest` + `alert_occurrence_labels` 子表）**MUST** 在关联每次送达前逐项复核，同一三元组不同 labels 记录 `identity_conflict`，**MUST NOT** 静默合并；身份与 labels 快照字段由 schema 触发器冻结（`trg_alert_occurrences_identity_immutable`、`trg_alert_occurrence_labels_no_update`）。（来源：CONTEXT「告警发生」「告警接入问题」）
- **DATA-ALERT-005 —** Occurrence 生命周期只有 `Firing | Resolved`，**MUST** 只由载荷中对应 `alerts[i].status` 推进；**MUST NOT** 使用顶层 status、groupKey、endsAt、截断缺失、来源停用或长期无通知推断；Resolved **MUST NOT** 被重新打开（触发器 `trg_alert_occurrence_no_reopen`）。（来源：CONTEXT「告警发生」）
- **DATA-ALERT-006 —** 每个有效项 **MUST** 形成不可变 `alert_observations`，记录 `effect`（`initial_firing`/`repeat_firing`/`resolved`/`resolved_first`/`late_firing_after_resolved`）；resolved-first 与 resolved 后迟到 firing **MUST** 保留观察且迟到 firing 不重开 Occurrence。`observed_state` 与 `effect` **MUST** 一致（`firing` 只对应三种 firing effect，`resolved` 只对应 `resolved`/`resolved_first`，schema CHECK 强制）。（来源：CONTEXT「告警观察」）
- **DATA-ALERT-007 —** 影响告警列表的 Occurrence 变更 **MUST** 在同一事务内维护 `row_version`（应用在 UPDATE 中递增）、`last_state_change_at`/`resolved_at`，并由触发器（`trg_alert_change_log_insert`/`trg_alert_change_log_state`）写入 `alert_change_log`。（来源：CONTEXT「实时投影」「告警列表与详情」；Rationale：SQLite 触发器不支持 `SET NEW`，时间与版本字段由应用在同一条 UPDATE 中维护。）
- **DATA-ALERT-008 —** 每条 Delivery **MUST** 携带认证元数据：`alert_deliveries.credential_id` 与 `credential_snapshot_version` **MUST** 非空（NOT NULL，快照版本 CHECK `>= 1`），Delivery 事务 **MUST** 重验来源启用、凭据有效性与归属（`credential_id` + 快照版本）；Delivery 与凭据吊销按 SQLite 提交顺序裁决，**MUST NOT** 使用墙钟宽限期。（来源：CONTEXT「告警源凭据投影」）
- **DATA-ALERT-009 —** 每个来源轮换期间 **MUST** 最多同时两个 `Active` 凭据（触发器强制），凭据唯一合法的 UPDATE **MUST** 是 `Active -> Retired`（`trg_alert_source_credentials_update_is_retirement`），因此 Retired 凭据 **MUST NOT** 复活或再被更新；`retired_at` 由应用在状态变更 UPDATE 中写入，且 `state` 与 `retired_at` 的一致性 **MUST** 由 CHECK 强制（Retired 必须有 `retired_at`，Active 必须无）；凭据 `row_version` **MUST** 从 1 起始，合法退休 **MUST** 恰好递增 1（`trg_alert_source_credentials_row_version_increment`）；吊销命令 **MUST** 携带 `expected_row_version` 并在同一 UPDATE 的 WHERE 中比较（DATA-COMMAND-005），同一事务写入 `retired_at`、递增 `row_version` 并提交命令结果；相同命令 ID 重放 **MUST** 返回原结果（DATA-COMMAND-003），新命令针对已 Retired 凭据 **MUST** 冲突；凭据来源字段（`source_id`/`digest`）与历史 **MUST** 不可改写、不可删除（`trg_alert_source_credentials_origin_immutable`、`trg_alert_source_credentials_no_delete`）。（来源：CONTEXT「告警源凭据投影」）
- **DATA-ALERT-010 —** `alert_sources.row_version` **MUST** 从 1 起始、任何 UPDATE 恰好递增 1（触发器）；enable/disable 命令 **MUST** 携带 `expected_row_version` 并在同一 UPDATE 的 WHERE 中比较（DATA-COMMAND-005）。（来源：CONTEXT「告警源凭据投影」）

- **DATA-RUNTIME-001 —** `runtime_slots` **MUST** 是注册状态与 current/pending 凭据指针的唯一权威：`slot`（固定两行）、`state`（`unregistered | registered | revoked`，仅允许 `unregistered->registered/revoked`、`registered->revoked`、`revoked->registered`，触发器 `trg_runtime_slots_state_transition`）、`current_credential_id`（当前 active 长期 token 的唯一选择，**MUST** 引用同 slot 且 `confirmed_at` 非空、`retired_at` 为空的行，触发器 `trg_runtime_slots_current_owner_insert/update`）、`pending_credential_id`（两阶段轮换待确认 token，**MUST** 引用同 slot 且 `retired_at` 为空的行，可已确认或未确认，触发器 `trg_runtime_slots_pending_owner_insert/update`；current/pending **MUST NOT** 指向同一行，表 CHECK）与 `row_version`（Admin 注册/替换/轮换命令并发前提，DATA-ROWVER-001）。表 CHECK **MUST** 强制：`registered` ⇔ `current_credential_id` 非空，`unregistered`/`revoked` ⇔ current/pending 皆空——因此每个语句/提交点 `registered` iff current 非空 iff 指向本 slot 已确认未退休凭据。在线连接、boot ID、connection epoch 与心跳 last_seen **MUST NOT** 落库——它们是内存瞬时投影（HTTP-RUNTIME-001），心跳 **MUST NOT** 改写 `runtime_slots` 的 `row_version`。替换（`registered->revoked`）**MUST** 在同一事务先确认 fence（DATA-RUNTIME-001b），否则 **MUST** 409 `active_conflict` 且 **MUST NOT** 先行吊销（触发器 `trg_runtime_slots_no_replace_with_active` 机械兜底）；替换事务顺序：单条 UPDATE 置 `revoked` 并清空 current/pending 指针 -> AFTER 触发器 `trg_runtime_slots_replace_retire_all` 自动 retire 该 slot 全部未退休凭据（被引用的行在指针清空前禁止手动 retire，`trg_runtime_credentials_no_retire_while_referenced`）。Attempt 派发 **MUST** 在同一事务复查目标 slot `registered` 且 `current_credential_id` 指向本 slot 已确认未退休凭据（触发器 `trg_execution_attempts_slot_registered(_update)`），替换与派发按 SQLite 提交顺序裁决：替换先提交则后续派发被拒，派发先提交则替换被拒。BrowserSession 瞬时锁（noVNC 重附着）**MUST** 在 Quoin 内存临界区与替换事务同 fence，**MUST NOT** 新增持久表。（来源：CONTEXT「服务身份」、Issue #11 前置审计）
- **DATA-RUNTIME-001b —** Execution Attempt 可由 Plinth 或 Lintel 承载（`browser_exploration` 与巡检 Journey 的子 Attempt 绑定 Lintel；CONTEXT「执行尝试」），Browser Operation 全部由 Lintel 承载。替换 fence 按 slot 检查：任意 slot 置 `revoked` 前 **MUST** 无绑定该 slot 的 active Attempt（`Assigned`/`Running`/`Cancelling`）；此外 `lintel` 置 `revoked` 前 **MUST** 无任何状态为 `Queued|WaitingForCapacity|Starting|Running|AwaitingReconnect` **或虽已终态但 `stop_confirmed_at` 仍为空**的 Browser Operation（直接检查，**MUST NOT** 经 Attempt 推断——manual login、probe、未派发 Journey、两次 Exploration action 之间仍活跃的 Session，以及领域结果已封存但物理进程尚未确认停止者都拦截）（触发器 `trg_runtime_slots_no_replace_with_active`）。只有全部 Browser Operation 已终态且已确认物理停止后替换才被允许。（来源：CONTEXT「浏览器身份」「服务身份」「执行尝试」、Issue #11 前置审计）
- **DATA-RUNTIME-002 —** Runtime 长期服务 token **MUST** 以不可变 credential generation 历史持久化（`runtime_credentials`，只存 32-byte SHA-256 digest）：来源字段（`slot`/`generation`/`token_digest`/`created_at`）**MUST** 不可改写（`trg_runtime_credentials_origin_immutable`）、历史 **MUST NOT** 删除（`trg_runtime_credentials_no_delete`）、`row_version` 恰好递增 1；`confirmed_at`（Runtime 持久化确认）与 `retired_at`（吊销）是两个一次性生命周期事实：NULL -> 时间戳各一次，不可回退、不可改写（`trg_runtime_credentials_confirmed_once`/`retired_once`）。本表**不保存状态列、不宣称 current**——当前选择只由 `runtime_slots.current_credential_id` 承载（DATA-RUNTIME-001）。被 current 或 pending 指针引用的 credential **MUST NOT** 被置 `retired_at`（`trg_runtime_credentials_no_retire_while_referenced`）；已退休凭据 **MUST NOT** 再被确认（`trg_runtime_credentials_no_confirm_after_retire`，确认与吊销互斥且各一次）；INSERT 时 `retired_at` **MUST** 为 NULL（不得“出生即退休”，`trg_runtime_credentials_insert_not_retired`）；`confirmed_at` 非 NULL 的 INSERT 只允许初次注册/替换后注册窗口（slot `unregistered`/`revoked` 且 current/pending 皆空，`trg_runtime_credentials_insert_confirmed_registration_only`）。确认（`confirmed_at` NULL->时间戳）**MUST** 只允许正被同 slot `pending_credential_id` 引用的行（`trg_runtime_credentials_confirm_requires_pending`）。合法轮换单事务顺序：建 credential（`confirmed_at` 空）-> 设 `pending_credential_id` -> Runtime 持久化确认后写 `confirmed_at`（NULL->时间戳，须仍被 pending 引用）-> 单条 UPDATE 原子提升：`current_credential_id` = 原 `pending_credential_id` 且 `pending_credential_id` 清空（`trg_runtime_slots_promote_requires_pending` 强制唯一路径：registered 上更换 current 只能是提升 pending，禁止绕 pending 直切、禁止先清 pending 后另行切换；owner/promotion 验证覆盖不同非法类别，任一 `RAISE(ABORT)` 都回滚整条 UPDATE 及此前触发器副作用，因此不依赖同类触发器的执行次序）——AFTER 触发器 `trg_runtime_slots_promotion_retire_old` 自动将旧 current 置 `retired_at` 并递增 `row_version`：retirement 是指针转移的机械副作用，应用 **MUST NOT** 事后手动 retire。中止：清空 `pending_credential_id`（current 不变），AFTER 触发器 `trg_runtime_slots_abort_retire_pending` 自动 retire 原 pending。registered slot 上 pending 指针 **MUST NOT** 从非 NULL 直接换绑到另一个非 NULL（`trg_runtime_slots_pending_no_direct_swap` 拒绝直接替换）——必须先 pending->NULL（自动 retire 原 pending）再 NULL->new；已退休凭据 **MUST NOT** 再被设为 pending（owner 触发器拒绝）。合法替换：置 slot `revoked` 并清空两指针，AFTER 触发器 `trg_runtime_slots_replace_retire_all` 自动 retire 该 slot 全部未退休凭据。认证/派发只接受 `registered` + current 指针指向的行，**MUST NOT** 接受未被指针选中的已确认历史行。一次性注册令牌 **MUST NOT** 落库（内存短生命周期、单次使用、绑定 slot 与 credential generation，HTTP-COMMAND-012）；长期 token 只经已认证 gRPC 控制面下发/轮换（`runtime-protocol.md` #11）。（来源：CONTEXT「服务身份」、Issue #11 前置审计）

## 11. 浏览器身份

- **DATA-BROWSER-001 —** 每个 Business System **MUST** 且只能有一个共享 Browser Identity。`browser_identities` 只保存稳定身份、`current_revision_id`、`current_profile_generation_id`、`Ready|AuthenticationRequired` 状态与并发版本；名称、规范化 `http|https` `start_url`、版本化 authentication-probe Journey 引用及其类型化参数 **MUST** 保存为不可变 `browser_identity_revisions`。每次配置修改创建新 revision 并原子切换当前指针；身份存在未停止 operation 时命令必须在创建 revision 前返回 `identity_busy`，不得建立延迟 probe 队列。每个 Browser Operation 在准入时冻结实际 identity revision，历史不得按当前配置重解释；revision 中的 catalog digest/version 是该 revision 创建时的静态校验来源，不是永久执行 pin。协调升级后，同一稳定 Journey ID 的兼容实现 version 可提高，新的 operation 必须冻结 Lintel 当前 ready catalog 的实际 digest/version/Journey version；CFG-JOURNEY-005 的构建门只机械证明 ID/version/steps-digest 结构事实，参数、输出、purpose 与 Evidence 契约是否保持不变由生成源评审负责，变化时必须使用新 ID。（来源：CONTEXT「浏览器身份」）
- **DATA-BROWSER-002 —** profile 文件本体 **MUST NOT** 进入 SQLite；`browser_profile_generations` **MUST** 追加不可变 generation 历史并冻结 identity revision、精确 Chromium revision、profile manifest digest、成功 probe 所用 catalog digest/version、发布 operation 与操作者。只有发起当前 `manual_login` 的同一用户在 probe 明确 `Authenticated` 后才能显式发布；发布结果事务 **MUST** 同时创建 generation、切换当前指针、把身份置 `Ready` 并把 operation 置 `Succeeded`。日常 Journey/Exploration 的 profile 变化不得自动制造 generation；当前 Lintel Chromium revision 与 generation 不完全相等时 **MUST NOT** 打开旧 profile，身份直接转 `AuthenticationRequired`。（来源：CONTEXT「浏览器身份」「浏览器操作记录」）
- **DATA-BROWSER-003 —** `browser_operations` 是会话级持久审计、唯一身份锁与全局容量 FIFO 的唯一权威，operation 状态、终止原因与停止确认 basis 的封闭集合以 `contracts/sql/schema.sql` 为唯一机器权威。`Starting` 与不可变 `start_dispatched_at`/Lintel boot+epoch 绑定表示 Start 已产生外部副作用但 Ack 结果未知；它计入容量并持续持有身份 fence，只有幂等 accepted Ack 才进入 `Running`；明确 `NO_CAPACITY` 可回到保留同一派发 binding 的 `WaitingForCapacity` 并按原 FIFO 重发；其他 Start reject 必须以 SQL 封闭映射收口：`authentication_required` 保持同名，`profile_unavailable` 按已知 inventory 事实精确化为 `profile_missing|profile_manifest_invalid|chromium_revision_mismatch`，`identity_busy|input_unsupported|reconcile_required|stale_stream|internal` 统一以 `protocol_error` 结束而原 reject reason 仍单独留审计；断流或新 boot 则进入中断收口。用户可见种类为 `manual_login|journey|exploration`；配置 revision 切换触发的内部 `authentication_probe` 同样使用该 ledger、容量和身份锁但不形成第四个人类操作入口。唯一部分索引 **MUST** 保证同一身份只有一个未停止 operation（包括领域已终态但尚未收到物理停止确认者）；身份已占用时不得排队：人工/Exploration 返回 `IdentityBusy`，Inspection/Config Test 立即形成 `identity_busy` gap。所有四类容量请求都必须在派发前创建该 ledger 行；全局 Lintel slot 不足才进入 `WaitingForCapacity`；调度只按 `browser_operations.id` 的 SQLite 提交创建序执行全局 FIFO，`requested_at` 只作显示时间。Inspection Run/Config Test Run 保持 `Running`，等待提示直接由其 operation 派生。领域终态可先提交，但身份锁与物理 slot 必须等 `stop_confirmed_at` 与匹配的封闭 `stop_confirmation_basis` 同时写入后释放；只有 Start 尚未派发（`not_dispatched`）或持久化 `accepted=false` 拒绝事实（`start_rejected`）明确证明未创建进程时，才可在终态事务内直接确认停止；Start 已派发但 Ack 丢失不得作此推断。正常停止 Ack 使用 `stop_ack`，同 boot 全量 inventory 明确缺席使用 `inventory_absent`，新 boot 证明旧进程消失使用 `new_boot`；后两者只确认物理停止，不改写既有领域 terminal reason。时间与 basis 必须成对且一次写入。（来源：CONTEXT「浏览器身份」「浏览器操作记录」）
- **DATA-BROWSER-004 —** `manual_login` 创建事务 **MUST** 立即把身份置 `AuthenticationRequired`；operation 绑定发起用户且任何时刻最多一个 active noVNC attachment。只有同一用户可在同 boot 宽限期重附着或发布；关闭、取消、宽限到期、Session 撤销、Quoin/Lintel 重启或 shutdown 均以 `Cancelled|Interrupted` 收口且保持 `AuthenticationRequired`。Quoin 启动时任何遗留 operation 都不得恢复业务执行，且在完成调和前不得接收新浏览器工作：未派发者直接以 `Interrupted|shutdown` 和 `not_dispatched` 原子收口；同一 Lintel boot 仍报告物理进程者只执行关闭清理，先尽力取得适用的强制 trace/completion probe，再以 `Interrupted|shutdown` 收口并等待停止确认；无法联系旧 boot 时以 `Interrupted|runtime_unavailable` 明确记录 trace 不可得；新 Lintel boot 以 `Interrupted|new_boot` 收口并可直接确认旧进程已不存在。BrowserSession 不跨进程恢复；同 boot 普通断流重连仍按控制流调和实际 active operation 集合并重发停止 fence。operation 状态终态后不可复活，只有一次性的 `stop_confirmed_at` 可随后写入；来源、冻结 revision/generation 与操作者不可改写。（来源：CONTEXT「浏览器身份」「浏览器操作记录」）
- **DATA-BROWSER-005 —** authentication probe **MUST** 记录为 `browser_probe_results` 三态事实：`Authenticated|Unauthenticated|Indeterminate`，并冻结 operation、phase、identity revision、实际执行 Journey ID/version、catalog digest/version 与结束时间。revision 中的 binding 只记录创建时校验 provenance；probe operation 使用当前 ready catalog 中同一稳定 ID 的兼容 version（不得低于 revision 记录版本）并冻结该次实际 binding。`Unauthenticated` 原子把身份置 `AuthenticationRequired`；`Indeterminate`（Runtime 离线、超时、浏览器崩溃、选择器失效等）只形成 `authentication_probe_unavailable`，不得改变原身份状态。identity revision 切换后立即以新配置对现有 generation 创建 probe operation；成功保持 `Ready` 且不创建 generation，明确未登录才降级。（来源：CONTEXT「浏览器身份」）
- **DATA-BROWSER-006 —** Journey 在单个 `inspection_collection` Attempt 下对应单个 `journey` operation；不得自动重跑整条 Journey 或从中间恢复。第一步前与成功提交前各执行 probe。success ResultProposal 必须携带唯一 primary structured Evidence，其 `result_json` 是 typed output 的唯一正文权威；业务 gap 的 `evidence` 固定为空，不制造占位 Evidence。不可变 `browser_journey_results` 以 operation 为唯一键保存规范摘要与封闭 outcome/gap 事实，success 另引用 primary Evidence；不复制 output 正文。强制 trace 提交失败时外层 gap 为 `artifact_commit_failed`，ledger 另以 `original_gap_code='journey_failed'` 保留被覆盖的原步骤失败分类。插入该 ledger 是单一提交入口：同一 statement 派生 check result并原子收口 operation 与 Attempt；同 digest 重放读取原记录重建 Ack，不同 digest 因 operation 唯一键拒绝。operation 创建前的 `identity_busy` ResultProposal 由 check result 保存 digest、无 Evidence，并原子把未派发 Queued Attempt 收口 `Succeeded`；这里的成功只表示合法 gap 已提交。Journey 失败必须提交一个整体敏感 trace；trace 提交失败时 check 原因 **MUST** 为 `artifact_commit_failed`，但不得丢失原步骤错误分类。（来源：CONTEXT「浏览器操作记录」「Journey Catalog」）
- **DATA-BROWSER-007 —** 一个 `exploration` operation **MUST** 聚合父 Investigation Attempt 下跨多个 Browser Tool Call 的有状态 Exploration Session；每个 Tool Call 仍创建独立 `browser_exploration` 子 Attempt；首个 `open` 子 Attempt 的 `browser_exploration_v1` 输入同时携带冻结 identity/profile/catalog 绑定，不得另建无传输路径的 Session 输入 Schema。通过身份准入后，以 `browser_exploration_actions` 唯一绑定同一 operation、Tool Call、子 Attempt 与递增 action sequence。`open` 在准入前命中 `IdentityBusy` 时不得伪造 operation/action：父 `quoin_browser` Tool Call 的终态 Result 是单一提交入口，AFTER trigger 在同一 statement 收口尚未派发的子 Attempt并引用当前占用事实；不得先单独提交子 Attempt 终态。Session 建立和成功关闭前各执行 probe；显式关闭、父 Attempt 准备终态、取消、lease 丢失、Runtime 断开、Chromium/profile 故障或强制 trace 提交失败才结束 Session。显式取消时父 Attempt 先进入 `Cancelling` 请求 Session 收口；自然成功/失败时父 Attempt 保持 `Running`，先提交 operation 与强制 trace，再直接进入对应终态。任何路径都不得由父状态更新直接伪造 operation 终局。可恢复动作失败只完成当前子 Attempt，不释放 Session/身份锁。（来源：CONTEXT「浏览器操作记录」「执行尝试」）
- **DATA-BROWSER-008 —** `browser_exploration_actions` 是有界结构化动作日志：只保存 action 类型、非秘密目标描述、page/origin、时间、结果/错误码、观察版本、摘要 hash/大小及 Artifact 引用；不得复制 fill/press 实际输入值、页面正文、Cookie、storage state 或网络正文。整个 Exploration Session **MUST** 只有一个连续敏感 trace；Lintel 按 operation ID 在临时 staging 中追加，结束时只提交一次不可变 Artifact，全部子 Attempt 经 action → operation 关系派生引用该 Artifact，不在逐动作输入/结果中携带尚未完成的 Artifact locator。已启动 Session 的异常结束可标 `incomplete`，但必须成功提交；无法提交时 operation 只能以 `Failed/artifact_commit_failed` 收口。`Succeeded` 必须具有 `complete` trace；仅 Start 尚未派发或 `accepted=false` 明确拒绝的 operation 可证明未建立 Session，终态无需伪造空 trace。若新 boot、Runtime 断流等使 Quoin 无法证明已派发 Start 是否启动进程且 trace 不可能取得，operation 必须以明确 `Interrupted/new_boot|runtime_unavailable` 审计事实收口，不得伪造空 trace 或误报 `artifact_commit_failed`。（来源：CONTEXT「浏览器操作记录」）

- **DATA-BROWSER-010 —** Browser Identity 写命令 **MUST** 携带 `expected_row_version`，成功精确 `row_version + 1`；创建身份不伪造版本前提。所有 Browser Operation、probe result、Exploration action 与 profile generation 都是持久历史，禁止删除；除明确状态机字段外来源列不可更新。（来源：CONTEXT「浏览器身份」「并发与命令幂等」）
- **DATA-BROWSER-011 —** `inspection_check_results` 与 `config_test_run_check_results` 的 `gap_reason` **MUST** 使用 `contracts/sql/schema.sql` 声明的同一封闭机器码集合；OpenAPI 对应字段必须由验证脚本逐项比对该权威集合，未知字符串不得落库或出现在 HTTP 成功响应中。`error|gap` 的人类说明属于上层诊断，不得取代机器码。（来源：CONTEXT「巡检运行」「浏览器身份」）

- **DATA-EMBED-002 —** 换模型 **MUST** 完整构建新 generation、校验后原子切换（`ux_embedding_generation_current`）；一次 cosine 检索 **MUST NOT** 混用 generation；程序 **MUST NOT** 设阈值或固定融合排名。`embedding_generations` 的 model/version/generation **MUST** 不可变；`vector_dim` 一旦设置或该 generation 已有 embeddings **MUST** 不可变更（`trg_embedding_generations_origin_immutable`、`trg_embedding_generations_vector_dim_immutable`）。（来源：CONTEXT「可复用知识」）
- **DATA-SSE-001 —** `alert_change_log` **MUST** 追加且禁止 UPDATE（触发器），其 `id`（AUTOINCREMENT）即单调递增 `alert_change_seq`，在同一事务内由数据库分配、永不复用；最新行（`MAX(id)`）**MUST** 由触发器保留、**MUST NOT** 被 GC 删除（`trg_alert_change_log_no_delete_latest`）；HTTP 快照 `snapshot_seq` **MUST** 取当前最大 `alert_change_log.id`。（来源：CONTEXT「实时投影」）
- **DATA-SSE-002 —** 客户端 `after`/`Last-Event-ID` 游标过期判定 **MUST** 使用 last-seen 谓词（DATA-SSE-009）：`high_water > 0` 时 `cursor < high_water AND cursor < oldest_available - 1` 判定过期；`high_water = 0` 时只有 `cursor = 0` 为当前。过期游标 **MUST** 触发 `resync_required`（HTTP-SSE-003 区分头前 410 与流内事件）；日志按部署配置保留有界窗口（旧行 GC 可 DELETE，最新行除外），可丢弃、可重建，**MUST NOT** 成为告警历史权威源。（来源：CONTEXT「实时投影」）
- **DATA-SSE-003 —** 变更事件只携带 Occurrence ID、变化类型（`created`/`state_changed`）与 row version；客户端按 sequence 与 row version 幂等应用，详情在版本变化后重新读取。（来源：CONTEXT「实时投影」）
- **DATA-SSE-004 —** `task_change_log` **MUST** 是任务快照/SSE 的有界派生变更投影：Initial Analysis、Execution Attempt、Inspection Run/Report、Tool Call、Knowledge Import Batch/Candidate、Browser Operation 与 Config Test Run 的创建与状态/阶段变化 **MUST** 在同一事务内写入 `object_type`/`object_id`/`row_version`/`change_type`（触发器保证）；其 `id`（AUTOINCREMENT）即单调递增 `task_change_seq`，**MUST NOT** 被复用；**MUST** 禁止 UPDATE，**MAY** 按保留窗口 DELETE（GC）；可丢弃、可重建，**MUST NOT** 成为任务历史权威源。（来源：CONTEXT「调查与巡检工作区」「后台任务提示」）
- **DATA-SSE-005 —** 所有可观察任务对象 **MUST** 携带 `row_version`：`initial_analyses`、`execution_attempts`、`inspection_runs`、`tool_calls`、`knowledge_import_batches`、`knowledge_candidates`、`browser_operations`、`config_test_runs`（schema 已统一；不可变 `inspection_reports` 固定以版本 1 投影）；`row_version` **MUST** 由应用在每次状态 UPDATE 中显式递增，`expected_row_version` 的比较与递增在同一条 UPDATE 的 WHERE/SET 中完成（SQLite 触发器不支持 `SET NEW`），并由 `trg_*_row_version_increment` 触发器验证恰好 +1（DATA-ROWVER-001）。（来源：CONTEXT「调查与巡检工作区」「领域写命令契约」）
- **DATA-SSE-006 —** 任务快照/SSE 客户端契约与告警一致：进入页面 **MUST** 先读 HTTP 快照（`snapshot_seq` 取当前最大 `task_change_log.id`，最新行由 `trg_task_change_log_no_delete_latest` 保留）再建立 SSE；重连 **MUST** 使用 `Last-Event-ID`；游标过期 **MUST** 返回 `resync_required` 并重新读取完整快照；事件只传对象 ID、变化类型与 row version。（来源：CONTEXT「调查与巡检工作区」「实时投影」）
- **DATA-SSE-007 —** 任务快照 **MUST** 是有界集合（HTTP-PAGE-007）：只包含 active 任务对象与当前用户已终态但尚未查看（`user_viewed` 投影）的任务对象；用户打开/标记查看后终态任务离开快照；快照按游标分页遍历，**MUST NOT** 返回历史 Report/Candidate/Attempt 等长期对象的全量集合。（来源：CONTEXT「调查与巡检工作区」「后台任务提示」）
- **DATA-SSE-009 —** 变更流回放水位 **MUST** 直接由日志本身派生，**MUST NOT** 建立第二张水位表：`high_water = COALESCE(MAX(change_log.id),0)`，`oldest_available = COALESCE(MIN(change_log.id),0)`；`alert_change_log`/`task_change_log` 各自的最新行 **MUST** 永远保留（`trg_alert_change_log_no_delete_latest`/`trg_task_change_log_no_delete_latest` 拒绝删除 `MAX(id)`），旧行仍可 GC 删除——因此 `high_water` 自首个事件后 **MUST NOT** 回退，`oldest_available` 只可能不降。客户端 `after`/`Last-Event-ID` 过期判定 **MUST** 使用 last-seen 谓词且以减法避免溢出：`high_water = 0`（从未分配任何 change_seq）时只有 `cursor = 0` 为当前；`high_water > 0` 时 `cursor < high_water AND cursor < oldest_available - 1` 判定过期（头前 410 / 流内 `resync_required`，HTTP-SSE-002/003）。推论：首事件后（`oldest = high = 1`）`after=0` 有效并回放首事件；`after = oldest - 1` 有效并回放 `oldest`；`after ≤ oldest - 2` 过期；`cursor == high_water`（刚取回的快照游标）恒为当前；全 GC 至仅剩最新行后 `oldest == high_water`，`after = high_water - 1` 仍可回放最新行，不存在 410 活锁。应用/客户端 **MUST NOT** 虚构水位（不存在可写的水位表）。（来源：CONTEXT「实时投影」）

## 16. Artifact 与保留

- **DATA-ARTIFACT-001 —** Artifact 发布 **MUST** 依序执行：临时文件与最终文件同一文件系统 → 写入并校验 hash/大小 → `fsync` 临时文件 → 按 SHA-256 原子 rename → `fsync` 最终父目录 → 才提交 SQLite 引用事务（同一事务插入或复用已核验物理正文的 `artifact_blobs` 并写入 `artifacts` 逻辑引用）；引用事务失败后 **MUST** 将文件作为孤儿清理。（来源：CONTEXT「Artifact 提交」、Issue #20 s6）
- **DATA-ARTIFACT-002 —** 每份内容 **MUST** 只有一个规范持久物理副本：`artifact_blobs.sha256` UNIQUE、`storage_key` 仅由 hash 推导；`artifacts` 通过 `blob_id` 引用物理副本并保存规范 `media_type`，允许同一 blob 被多个逻辑 Artifact 以不同 owner/kind/sensitive/retention 引用。大型 Tool 输出只是 `kind='tool_result'`、`retention_kind='generated'`、owner 为 Tool Call 的现有 Artifact，**MUST NOT** 生造 `.quoin/tool-results`、per-Attempt 持久目录、第二套索引或文件权威。（来源：CONTEXT「产物」、Issue #13 用户定案）
- **DATA-ARTIFACT-003 —** 访问、下载授权、保留与审计 **MUST** 按逻辑 `artifacts` 裁决。`kind + owner_type` 是封闭联合：`attachment+source_material`、`tool_result+tool_call`、`screenshot|trace+browser_operation`、`report_file+investigation_message|evidence|inspection_report|backup`，`owner_id` 必须在 INSERT 时机械闭合到对应权威表；Text Attachment 先创建 `source_materials(kind='text_attachment')`，Artifact 以该 Source Material 为 owner，再由 `text_attachments.artifact_id` 完成关联，禁止以尚不存在的 Text Attachment 行形成循环所有权。Raw trace 固定 sensitive，不进入模型上下文。生成型大 Artifact 默认保留 90 天（部署级配置），创建时固定 `expires_at`；到期保留元数据、media type、SHA-256、来源、时间并将 `body_expired` 从 0 单向置为 1，过期后不得复活；逻辑来源、到期时刻与物理 blob 身份不可改写/删除。Plinth 对当前 Attempt 获授权的非敏感 Artifact 只能通过 Quoin 的受控分段 Read/Grep 工具读取，使用 Artifact ID/offset/limit 或查询参数，**MUST NOT** 暴露 Quoin PV 物理路径、允许目录遍历或读取 Raw trace。（来源：CONTEXT「在线保留」「浏览器操作记录」「产物」、Issue #13）
- **DATA-ARTIFACT-004 —** Artifact GC 只在同一 `artifact_blobs` 的全部逻辑引用均已 `body_expired=1` 且与备份互斥时删除 `storage_key` 对应的物理文件；`artifact_blobs` 与 `artifacts` 元数据行永久保留，受 FK RESTRICT/append-only 约束，不做不可达的行 DELETE。单个引用过期不得删除仍被其他未过期引用需要的正文。以后再次发布相同 SHA-256 时，发布程序必须先重新物化、校验并 `fsync` 规范物理文件，再复用既有 blob 行创建新的未过期逻辑 Artifact；既有过期引用仍拒绝正文读取。（来源：CONTEXT「一致备份」「产物」）
- **DATA-ARTIFACT-005 —** 撤回消息、停用系统或停止复用知识 **MUST NOT** 删除来源历史；结构化告警、调查、消息、诊断、报告、反馈、知识、Text Attachment 与 Import Batch 原文长期保留。（来源：CONTEXT「在线保留」）
- **DATA-ARTIFACT-006 —** Runtime Artifact 上传 **MUST** 经幂等 ledger（`runtime_artifact_uploads`）：`upload_id` **MUST** 唯一且在整个重试生命周期稳定，绑定 `attempt_id`、`boot_id`、`connection_epoch`、逻辑 owner（`owner_type`/`owner_id`）、`kind`/`media_type`/`retention_kind`/`sensitive`、`size_bytes` 与 `sha256`（来源字段不可改写，`trg_runtime_artifact_uploads_origin_immutable`，含 `boot_id`）；同 `upload_id` 同摘要重试 **MUST** 返回原 `artifact_id`（应用按 ledger 裁决），同 `upload_id` 不同摘要/owner **MUST** 冲突拒绝。ledger 行 **MUST** 以 `state='uploading'` 创建（禁止直接 INSERT committed/rejected，`trg_runtime_artifact_uploads_insert_state`），状态转换仅 `uploading -> committed | rejected` 且终态不可变（`trg_runtime_artifact_uploads_state_transition`）；`committed` **MUST** 带 `artifact_id` 与 `committed_at`（CHECK）且满足 NULL-safe 正向条件（`trg_runtime_artifact_uploads_commit_attempt`）：所引 Attempt **MUST** `state='Running'` 且 `runtime_slot`/`boot_id`/`connection_epoch` 全部非空并与 upload 的 `boot_id`/`connection_epoch` 一致，同时 **MUST** JOIN `NEW.artifact_id` 对应 `artifacts` 与 `artifact_blobs` 并精确匹配 ledger 的 `sha256`/`size_bytes`/`kind`/`media_type`/`retention_kind`/`sensitive`/`owner_type`/`owner_id`——任何 NULL/不存在/任一不一致一律拒绝 commit，只能 `rejected`（旧 Attempt 已终态或替换后 ABA 不能 commit；协议后续还检查当前控制流 envelope）；`artifact_id`/`committed_at` 一旦提交 **MUST** 不可改（`trg_runtime_artifact_uploads_result_immutable`）；trace 上传必须 `sensitive=1`（CHECK）；历史 **MUST NOT** 删除。v1 **MUST** 整单重传，**MUST NOT** 实现 offset 续传。（来源：CONTEXT「产物」「Artifact 提交」、Issue #11 前置审计）
- **DATA-ARTIFACT-007 —** Tool 结果字节数 `> 50 * 1024` 或行数 `> 2000`（任一先满足）时 **MUST** 通过有界流直接提交为现有 `tool_result` Artifact；模型上下文只接收可判别预览、Artifact ID、media type、字节数、行数与 SHA-256，并被明确告知可调用 Artifact Read/Grep。文件/搜索结果预览优先头部，日志/命令输出优先尾部；写入、hash、上传或 Artifact 引用事务任一步失败时 Tool Call 必须 `failed`/Attempt 依据工作模式收敛，**MUST NOT** 静默把截断片段当完整结果。小结果可 inline JSON，但仍受模型输入预算和 Evidence 正文唯一位置约束。（来源：Issue #13 用户定案；Pi/OpenCode 上游机制研究）

- **DATA-BACKUP-005 —** 恢复后 **MUST** 保持维护状态并暂停调度：清除全部 Web Session；通过 TTY 选择恢复 Admin 并设临时密码；Runtime、Stele service token 与告警源 Bearer 全部失效并重新注册/轮换；Connection 密文保留但置 `revalidation_required=1`（DATA-CONN-003 阻断派发）；Browser Identity 置 `AuthenticationRequired`；Admin 检查后才退出维护状态。（来源：CONTEXT「一致备份」）
- **DATA-BACKUP-006 —** 备份目录只允许 Quoin UID 与部署操作者访问；恢复只由拥有 PVC/数据目录与根密钥权限的部署操作者在停机时执行；Admin 可浏览、显式下载和立即触发备份，下载审计。（来源：CONTEXT「一致备份」）
- **DATA-BACKUP-007 —** 备份记录（`backups`）**MUST** 追加且不可改写（`trg_backups_no_update`）；`status='succeeded'` **MUST** 带 `db_sha256`、`manifest_sha256` 与 `manifest_path`（CHECK 强制），`failed` 记录保留 `error_detail`。（来源：CONTEXT「一致备份」、Issue #20）

## 19. 事务程序与提交顺序裁决

**Non-normative：** SQLite WAL 单写者模型下，所有并发不变量最终依赖提交顺序；本文件要求写事务使用 `BEGIN IMMEDIATE` 并在同一事务内完成下列重验/裁决步骤。DATA-TX-001 至 DATA-TX-018 为规范条款，各自定义确定的事务步骤与提交顺序裁决规则。

- **DATA-TX-001 —** 所有领域写事务 **MUST** 以 `BEGIN IMMEDIATE` 获取写锁；状态竞争 **MUST** 按 SQLite 提交顺序裁决，**MUST NOT** 使用来源时间或墙钟决定先后。（来源：CONTEXT「告警观察」「告警源凭据投影」）
- **DATA-TX-002 —** 权限写事务提交前 **MUST** 在同一事务重验用户 `enabled`、`role`、`auth_revision`；账号变更（禁用/角色变化/改密）事务与业务写事务按提交顺序裁决：账号变更先提交则业务写冲突，业务写先提交则有效。（来源：CONTEXT「本地账号认证」）
- **DATA-TX-003 —** Delivery 事务 **MUST** 在提交前重验来源启用、凭据有效性与归属；吊销事务先提交则 Delivery 被拒绝且不创建 Occurrence，Delivery 先提交则有效。两事务按提交顺序裁决。（来源：CONTEXT「告警源凭据投影」）
- **DATA-TX-004 —** Attempt 派发事务 **MUST** 检查 Runtime slot、输入快照、固定 release/agent 版本，并为 chat/embedding 创建或复核 `attempt_connection_grants`；工具授权事务按 Tool Call 解析 Thanos 或 Business System 当前 Kubernetes mappings，再创建不可变 grant。连接停用、轮换、映射退休或 RevalidationRequired 先提交则新 grant/派发拒绝；已接受 Attempt 使用内存旧快照完成。（来源：CONTEXT「连接」「执行尝试」、Issue #13）
- **DATA-TX-005 —** 取消 fence 提交与成功结果提交按 SQLite 提交顺序裁决：成功先提交则取消返回已完成；取消（fence）先提交则迟到结果不产生有效消息/Report/Candidate，只留审计（DATA-ATTEMPT-003/004）。fence 与 transport detach 并发时，一旦 fence 提交任务 **MUST** 终态为 `Cancelled`，**MUST NOT** 停留在 `fenced` 中间态。（来源：CONTEXT「执行尝试」、Issue #18 原型证据）

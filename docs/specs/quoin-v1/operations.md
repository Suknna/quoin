# Quoin v1 运维与部署规格

**状态：Draft**

**Non-normative：** 本文件（CATEGORY=`OPS`）承载 Quoin v1 的 Compose、Helm、进程配置、容器镜像、卷与锁、健康检查、可观测性、备份恢复包装、发布供应链、离线分发、升级与部署验收语义。HTTP 路由与字段由 [`contracts/openapi.yaml`](contracts/openapi.yaml) 拥有，SQLite 字段与约束由 [`contracts/sql/schema.sql`](contracts/sql/schema.sql) 拥有，Runtime wire 枚举由 [`contracts/runtime.proto`](contracts/runtime.proto) 拥有，部署文档形状由 [`contracts/schemas/deployment-config.schema.json`](contracts/schemas/deployment-config.schema.json) 拥有，发布 manifest 形状由 [`contracts/schemas/release-manifest.schema.json`](contracts/schemas/release-manifest.schema.json) 拥有，自定义指标 family 由 [`contracts/metrics.yaml`](contracts/metrics.yaml) 拥有，Plinth worker 本地工具目录由 [`contracts/plinth-worker-tools.yaml`](contracts/plinth-worker-tools.yaml) 拥有。本文件不复制这些机器契约的完整字段或枚举。

## 1. 范围与事实所有权

- **OPS-SCOPE-001 —** Admin 可理解的运维设置（备份时间、IANA 时区、备份保留份数和生成型 Artifact 保留天数）**MUST** 只由 Admin Web UI 管理并持久化到 SQLite；部署配置 **MUST** 只保存 public Origin、卷与 Secret/file 路径、外部 TLS 接入和少量不可由产品推导的基础设施事实，两类字段 **MUST NOT** 重叠。（来源：[CONTEXT「存储、保留与部署」](../../../CONTEXT.md#存储保留与部署)、[Issue #17](https://github.com/Suknna/quoin/issues/17)）
- **OPS-SCOPE-002 —** `contracts/schemas/deployment-config.schema.json` **MUST** 是 Helm 与 Compose 共用的进程部署配置唯一机器权威；Chart `values.schema.json`、Compose 最少输入和四组件配置文件 **MUST** 由它生成或由 fixture 证明机械投影相等，且 **MUST NOT** 建立第二份字段定义。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.1、Q17.20）
- **OPS-SCOPE-003 —** 部署配置 **MUST NOT** 拥有镜像版本、容器内部监听地址或端口、replica/HPA、Admin 运维设置、SQLite durability、Artifact GC 周期或 batch size；镜像由 Release manifest 拥有，固定内部端口和进程内部调优由本文件拥有。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.1、Q17.22、Q17.42）

## 2. 进程配置与投影

- **OPS-CONFIG-001 —** `deployment-config.schema.json` **MUST** 同时拥有 Helm/Compose 人类最少安装输入与四组件生成配置：安装输入以 `document=helm-install|compose-install` 判别，组件配置以 `component` 判别；全部对象 **MUST** 拒绝未知字段。每个组件只接受固定 `--config /etc/quoin/<component>.yaml`，生成器只投影其实际消费的组件分支。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.20）
- **OPS-CONFIG-002 —** 进程配置 **MUST** 在启动时读取一次并在该进程生命周期内保持不可变；变更 **MUST** 通过零重叠显式重启生效，第一版 **MUST NOT** 提供文件 watcher 或 `SIGHUP` reload。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.1）
- **OPS-CONFIG-003 —** Secret、根密钥、服务 token 与私钥 **MUST** 只以独立只读文件路径出现在配置中；配置 **MUST NOT** 承载 secret value。实现 **MUST NOT** 为 Schema 字段再提供同义环境变量或重复 CLI flag，也 **MUST NOT** 定义多来源优先级。（来源：[SEC-KEY-001](security.md#5-根密钥与可逆连接秘密)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.20）
- **OPS-CONFIG-004 —** Admin Web UI + SQLite 设置 **MUST** 按其领域命令即时生效且不依赖进程配置 reload；部署生成器 **MUST** 只把每个组件实际消费的 `$defs` 投影为该组件的最小文档。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.1、Q17.20）
- **OPS-CONFIG-005 —** Helm values **MUST** 要求公共 Origin、Ingress 接入、四个持久卷的容量/access mode/可选 StorageClass 与 Lintel browser slots；省略时 `/dev/shm` **MUST** 默认为 1 GiB、监控发现方式 **MUST** 默认为 `none`、PrometheusRule **MUST** 默认为不生成。Compose 输入 **MUST** 要求公共 Origin、`publishMode=loopback|internal-network-only`、host port（仅 loopback）、internal-network-only 时的 existing proxy network 名、宿主 secret 目录与 browser slots；省略时 shm **MUST** 默认为 1 GiB。资源 requests/limits 与监控 annotation **MAY** 显式配置；replica、内部端口、内部路径、镜像版本、volume 名、探针阈值与安全开关 **MUST NOT** 暴露。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.20/Q17.30/Q17.31/Q17.37/Q17.42）
- **OPS-PACKAGE-001 —** Chart 与 Compose bundle **MUST** 是可独立安装的完整投影：包含四组件 workload/service/volume/security/probe 配置、Schema 校验、首次秘密 bootstrap、`quoin-deploy` 向导入口和最少输入示例；不得把实现留给未定义的人工步骤。release 工件名称、OCI repository 与 digest **MUST** 由 Release manifest 拥有。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.33/Q17.37）
- **OPS-PACKAGE-002 —** `contracts/schemas/metrics.schema.json`、`plinth-worker-tools.schema.json`、`release-inputs.schema.json`、`readiness-response.schema.json` 与 `release-manifest.schema.json` **MUST** 分别校验指标目录、Plinth 工具目录、基础镜像/浏览器/Lintel package 依赖锁、readiness 响应与发布投影；发布门 **MUST** 以机器解析证明实际 Chart/Compose/镜像内容严格等于这些权威源，而不是只证明 YAML/JSON 可解析。（来源：[SPEC-AUTHORITY-003](README.md#权威源与事实所有权)、Issue #17 Q17.23/Q17.35/Q17.36/Q17.37）
- **OPS-PACKAGE-003 —** `quoin-deploy compose|helm install` **MUST** 在启动长期 Quoin 前按“秘密 bootstrap 成功 → Admin bootstrap 成功或确认已有用户 → 长期 workload”严格串行。只对已证明无 `users` 行的空白数据库，经 attached TTY 收集 username、display name 与临时密码，调用同一 Quoin 镜像的离线 `quoin admin create`，并确认 `password_change_required=1` 后才解除启动门；已有用户时该阶段只验证存在性，不得自动创建或重置。Compose **MUST** 用两个一次性 service 串行，并让全部长期 service 以 `depends_on.condition=service_completed_successfully` 依赖 Admin bootstrap。Helm helper **MUST** 在调用 `helm install` 创建任何长期 Deployment **之前**，先从已校验的 Helm 输入投影并应用固定名称的 retained PVC/Secret、运行秘密 bootstrap Job，再运行挂载同一 data PVC 与只读根密钥 Secret 的 Admin bootstrap Job；PVC 对象只由 helper 物化，Chart 模板 **MUST NOT** 渲染或接管 PVC，只能按固定 claim name 引用。两者成功后才写入无秘密的固定 bootstrap-complete ConfigMap；Chart **MUST** 以 `lookup` 发现标记缺失或内容不符即 `fail`，随后才创建固定一个副本的长期 Deployment。Job 以 `kubectl attach` 传入输入并在完成后删除短生命周期 Job/RBAC；任一 bootstrap Job 失败时 helper **MUST** 删除失败的短生命周期 Job/ServiceAccount/Role 后再允许重建重试，且 **MUST NOT** 删除已持久化 data/PVC/Secret、创建完成标记或启动长期 workload。重试从已持久化阶段幂等继续。输入不得进入 values、Secret、argv、环境、history 或日志；Chart/Compose **MUST NOT** 暴露绕过该内部门的用户设置。（来源：CONTEXT「管理员离线恢复」、SEC-AUTHZ-002、SEC-PASSWORD-007）

## 3. 网络、TLS 与固定端口

- **OPS-NET-001 —** Quoin **MUST NOT** 签发公共证书或捆绑 Ingress Controller、cert-manager、Caddy、Nginx；Helm **MUST** 接入部署者已有的 IngressClass 与 TLS Secret，Compose **MUST** 接入已有反向代理与证书。public Origin **MUST** 显式配置且 **MUST NOT** 从 `Host`/`Forwarded` 临时推导。（来源：[SEC-CSRF-003](security.md#3-session同源请求与浏览器响应)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.5）
- **OPS-NET-002 —** 容器内部端口 **MUST** 固定为：Quoin public HTTP `8080`、Quoin Runtime gRPC `8443`、四组件 ops `9090`、Stele webhook 在自身容器使用 `8080`；进程配置 **MUST NOT** 改写内部 host/port，只有 Compose host publish 与 Kubernetes Service/Ingress 外部映射 **MAY** 配置。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.30、Q17.42）
- **OPS-NET-003 —** Helm **MUST** 为 Quoin public、Quoin Runtime gRPC、Stele webhook 和四组件 ops 建立职责分离的 ClusterIP Service；Plinth/Lintel **MUST NOT** 创建业务入站 Service，Runtime 与 ops **MUST NOT** 进入 public Ingress。（来源：[CONTEXT「服务暴露拓扑」](../../../CONTEXT.md#存储保留与部署)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.30）
- **OPS-NET-004 —** Compose 默认 **MUST** 只把 Quoin public 与 Stele webhook publish 到 `127.0.0.1` 的部署输入端口；Runtime 与全部 ops **MUST** 只 `expose` 在内部 network。部署者 **MAY** 把已有代理接入该 network 后关闭 loopback publish。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.30）

## 4. 运维端点、探针与关停

- **OPS-HEALTH-001 —** 四组件 **MUST** 在独立 ops listener 提供 `/livez`、`/readyz` 与 `/metrics`；这些端点 **MUST NOT** 进入产品 OpenAPI，也 **MUST NOT** 实现应用层认证。Helm **MAY** 在部署者显式启用且集群已有相应 CRD 时生成 ServiceMonitor/PodMonitor，基础 Chart **MUST NOT** 强依赖 Prometheus Operator 或猜测部署专属 NetworkPolicy。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.6）
- **OPS-HEALTH-002 —** `/livez` **MUST** 只判断本进程能否继续推进且不存在本地不可恢复 fatal state，**MUST NOT** 依赖 Quoin peer、外部系统、maintenance 或磁盘余量；`startupProbe` **MUST** 只等待 ops listener 启动。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.14）
- **OPS-HEALTH-003 —** `/readyz` **MUST** 判断组件能否承担其职责并返回由 `$id=https://github.com/Suknna/quoin/schemas/readiness-response.schema.json`（`contracts/schemas/readiness-response.schema.json`）唯一拥有字段、枚举与字段关系的固定 JSON；Ready 返回 200，not ready 返回 503。响应 **MUST NOT** 返回动态错误文本或新增机器契约未登记的 reason。探针 period、timeout 与 failure threshold **MUST** 由打包清单拥有并经慢 migration/慢启动测试，**MUST NOT** 成为用户设置。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.13、Q17.14）
- **OPS-HEALTH-004 —** Quoin 在取得数据目录锁并完成 migration 前 **MUST NOT** Ready；migration 完成且 maintenance-safe API 可用后，即使仍处于 maintenance，`/readyz` **MUST** 返回 200 并声明 `mode=maintenance`、`acceptingWork=false`，普通工作仍由维护门禁拒绝。（来源：[HTTP-MAINT-001](http-api.md#31-维护隔离)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.13）
- **OPS-HEALTH-005 —** Plinth/Lintel 只有在 token、严格版本握手和控制流被 Quoin 接受后才 **MUST** Ready；Stele 只有在版本握手与告警源 credential digest snapshot 加载成功后才 **MUST** Ready。Quoin 暂时离线时 Runtime **MUST** 保持 live 但 not ready，且 **MUST NOT** 因 peer 离线触发循环重启。（来源：[RUNTIME-AUTH-004](runtime-protocol.md#2-身份与认证)、[RUNTIME-CTRL-003](runtime-protocol.md#3-连接与握手runtimecontrolconnect)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.13）
- **OPS-HEALTH-006 —** `/livez` **MUST** 在 healthy 时返回 HTTP 200 与固定 `text/plain; charset=utf-8` 正文 `ok\n`，本地不可恢复 fatal state 返回 HTTP 500 与固定正文 `fatal\n`；`/metrics` **MUST** 使用 Prometheus text exposition content type。收到 SIGTERM 后，`/readyz` **MUST** 立即返回 503、`reason=draining`、`acceptingWork=false`，但 `/livez` 在进程仍能执行关停收口时继续返回 200；进程退出后由连接失败表达停止，**MUST NOT** 在退出前伪造 fatal。（来源：Issue #17 Q17.13/Q17.14/Q17.29）
- **OPS-SHUTDOWN-001 —** Kubernetes `terminationGracePeriodSeconds` 与 Compose `stop_grace_period` **MUST** 均为 60 秒；SIGTERM 后组件 **MUST** 立即停止新准入，最多使用前 45 秒完成当前 SQLite 事务、Artifact 原子发布、in-flight HTTP/Stele 请求、Runtime GoAway/结果确认和 Browser stop/incomplete trace 收口，并至少保留 15 秒关闭连接和退出。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.29）
- **OPS-SHUTDOWN-002 —** 关停 **MUST NOT** 等待任意长模型或浏览器工作自然完成，也 **MUST NOT** 把未完成工作伪装为 Cancelled/Success；实现 **MUST** 复用既有 fence/reconcile 语义。清单 **MUST NOT** 使用 sleep 型 preStop hook，核心关停 **MUST** 由幂等 SIGTERM handler 实现。（来源：[RUNTIME-TASK-004](runtime-protocol.md#4-任务派发与调和)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.29）

## 5. 拓扑、卷与进程锁

- **OPS-TOPOLOGY-001 —** 第一版 **MUST** 固定 Quoin、Plinth、Lintel、Stele 各一个 active replica，Helm 与 Compose **MUST** 使用零重叠替换，Kubernetes Deployment **MUST** 使用 `Recreate`；第一版 **MUST NOT** 提供 replicas 或 HPA 配置。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.12）
- **OPS-TOPOLOGY-002 —** Quoin、Plinth、Lintel **MUST** 分别在 `quoin-data`、`plinth-state`、`lintel-state` 固定 lock file 上取得非阻塞内核 advisory exclusive lock并持有文件描述符到退出；锁失败 **MUST** 立即以稳定错误码退出，lock file **MUST NOT** 被当作 PID 权威或通过删除“陈旧 PID”绕过。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.12）
- **OPS-TOPOLOGY-003 —** Quoin 服务、migration、restore 与 root-key rebind **MUST** 争用同一个 `quoin-data` 锁。SQLite WAL 数据卷 **MUST** 使用本地或块存储且 **MUST NOT** 使用 NFS/SMB；CSI 支持时 **SHOULD** 使用 `ReadWriteOncePod`，否则 **MUST** 使用 `ReadWriteOnce + Recreate + 应用锁`。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.12）
- **OPS-STORAGE-001 —** `quoin-data` **MUST** 同卷保存 SQLite、Artifact staging 与最终文件以满足 [DATA-ARTIFACT-001](persistence.md#16-artifact-与保留) 的同文件系统原子 rename；`quoin-backup` **MUST** 是独立卷，`plinth-state` 与 `lintel-state` **MUST** 各自独立，Stele **MUST NOT** 挂载持久卷。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.3）
- **OPS-STORAGE-002 —** 只有 Attempt workspace、普通 `/tmp` 与 Lintel 专用 `/dev/shm` **MAY** 使用可丢弃卷；Lintel `/dev/shm` **MUST** 使用 memory-backed emptyDir/tmpfs，Helm/Compose 安装输入省略时默认 1 GiB，生成器 **MUST** 把解析后的字节下限投影为 Lintel `minimumShmBytes`。Lintel 启动时 **MUST** 验证 `/dev/shm` 可写且实测总容量不小于 `minimumShmBytes`，不满足时 fail closed；**MUST NOT** 静默使用 `--disable-dev-shm-usage` 回退普通 `/tmp`。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.31）
- **OPS-STORAGE-003 —** 第一版 **MUST NOT** 默认设置 CPU/内存 limits；Helm requests/limits **MAY** 显式提供且默认空。Kubernetes PVC 容量 **MUST** 由部署操作者显式填写；Compose named volume **MUST NOT** 施加应用层容量限制。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.11）
- **OPS-STORAGE-004 —** 已知大小的 Artifact/备份操作 **MUST** 对目标目录和所需字节执行精确 preflight；`ENOSPC`、`EDQUOT`、`EROFS` 或持久化 fsync/rename 失败 **MUST** 把对应 storage health 置为不可写、令 Quoin not ready 并在 SQLite 仍可写时把当前领域任务或 Backup Run 持久化为稳定失败。恢复 **MUST** 在同一目录通过 create→write→fsync→rename→父目录 fsync→unlink probe 和当前操作 preflight，且 **MUST NOT** 依赖统一剩余百分比、静默删历史、隐藏预留文件或自动扩容。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.28）

## 6. 备份、恢复与 Artifact GC

- **OPS-BACKUP-001 —** `backups` **MUST** 是状态为 `queued|running|succeeded|failed` 的受限状态机聚合，只允许前向迁移，终态后不可修改，任何状态均禁止 DELETE；任一时刻最多一个 active Backup Run。具体字段、CHECK、索引与触发器只由 `contracts/sql/schema.sql` 拥有。（来源：[DATA-BACKUP-007](persistence.md#17-备份与恢复)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.21）
- **OPS-BACKUP-002 —** `triggerBackup` **MUST** 先持久化 active row 再返回 202；同一 `client_command_id` 重试 **MUST** 返回同一 row，其他手动触发 **MUST** 返回带 active ID 的冲突，定时触发 **MUST** 与 active run 合并而不排队第二份。启动时先按 OPS-BACKUP-003 收敛上一进程遗留 active row；随后调度器只在 normal mode、storage writable 且不存在 active run 时，按 `backups.scheduled_for` 中最后已观察 UTC 计划边界（无行时按备份设置启用时间）计算停机期间错过的触发，并最多为最新边界创建一份 `trigger_kind=scheduled`、`execution_mode=online` Run；`scheduled_for` 唯一索引 **MUST** 使该边界的重试或并发启动只能命中原行，完成这一轮 catch-up 判定后才开放下一次正常计划触发。第一版 **MUST NOT** 提供取消备份。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.21）
- **OPS-BACKUP-003 —** Quoin 启动时 **MUST** 在开放新触发前把上一进程遗留的 `queued|running` 行收敛为 `failed`，记录稳定进程中断错误码与结束时间；失败 **MUST NOT** 删除旧成功备份，后续正常周期 **MUST** 继续。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.21）
- **OPS-BACKUP-004 —** 备份执行、manifest/checksum 门禁、Artifact 精确集合、目录 fsync、恢复后信任重建与敏感下载 **MUST** 分别遵守 [DATA-BACKUP-001..007](persistence.md#17-备份与恢复)、[SEC-RESTORE-001..004](security.md#9-备份恢复维护与信任重建) 与 [HTTP-FILE-006](http-api.md#9-上传与下载)；`integrity_check` **MUST NOT** 替代已完整发布的 manifest+checksum。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.4、Q17.8）

## 10. Release manifest、供应链与离线分发

- **OPS-RELEASE-001 —** 每个 annotated SemVer tag **MUST** 产生唯一 `release-manifest.json`，其形状由 `contracts/schemas/release-manifest.schema.json` 拥有；Helm chart version 与 `quoin-<version>.tgz` **MUST** 取移除 tag 单个前导 `v` 后的完整 SemVer，Compose/离线资产名 **MUST** 保留完整 `v<version>`；source commit、四镜像 index/per-platform digest、浏览器 revision/每架构 SHA-256、基础镜像锁、OCI Chart repository/digest、Compose 与两个架构的 `quoin-deploy` 资产名/SHA-256、离线归档及其外置 Sigstore bundle 的确定性资产名、配置/DB/Proto/catalog version 与结构化验收摘要 **MUST** 从各自机器权威或依赖锁机械读取并断言相等，**MUST NOT** 手填。manifest **MUST NOT** 记录包含其自身的离线归档 hash；该归档完整性只由外部签名 bundle 绑定，避免哈希自引用。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.36）
- **OPS-RELEASE-002 —** 运行清单 **MUST** 只消费 digest，**MUST NOT** 发布或引用 `latest`；Chart 与 Compose **MUST** 只投影同一 Release manifest 并 **MUST NOT** 维护独立镜像版本表。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.36）
- **OPS-RELEASE-003 —** Helm Chart **MUST** 以 Release manifest 记录的 OCI repository + digest 发布并附同一生成 `.tgz`；Compose `.tar.gz` **MUST** 只包含 digest-pinned `compose.yaml`、最少输入模板、Schema 与 `quoin-deploy` 入口，且 **MUST NOT** 包含 Release manifest，以避免 manifest 记录容器自身哈希。Release 必须另附由 manifest 分别锁定 SHA-256 的 `quoin-deploy-linux-amd64` 与 `quoin-deploy-linux-arm64` 单文件资产；部署者下载后统一以 `quoin-deploy` 命令调用。文档中的命令 **MUST** 直接使用 manifest 字段，不得出现 registry/chart/asset 占位符。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.34/Q17.37）
- **OPS-SUPPLY-001 —** 四镜像 **MUST** 由 BuildKit 生成 SPDX SBOM attestation 与 SLSA provenance v1 `mode=min`；CI **MUST** 使用 Sigstore/cosign OIDC keyless 身份签署 image index、每平台 manifest、OCI Chart、Release manifest、Compose bundle、两个架构的 `quoin-deploy` 与离线归档，并保存可离线验证的 Sigstore bundle；其可发现资产名由 Release manifest 的 `sigstore_bundles` 封闭映射拥有。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.38）
- **OPS-SUPPLY-002 —** 发布门 **MUST** 验证 certificate identity/issuer；每个外部 Sigstore bundle 的 `subjectDigest` 必须等于其被签对象的 SHA-256（OCI image/Chart 使用 OCI digest，Release manifest/Compose/`quoin-deploy`/offline blob 使用资产字节 SHA-256），每个 SBOM/provenance attestation 的 subject 必须等于对应 image manifest digest。签名 subject 本身不写回被签对象，避免自引用。发布系统 **MUST NOT** 保存长期签名私钥。`contracts/release-inputs.yaml` **MUST** 锁定四组件基础镜像的 index/per-platform digest、Playwright tag 的 `browsers.json`/registry/native-deps 源码 SHA-256、Chromium 双架构工件 SHA-256 与 Lintel Debian package 完整版本；`plinth-worker-tools.yaml` **MUST** 锁定 Plinth 直接安装 package 的完整版本。任一实际锁定 package 版本、工具路径/版本、上游 descriptor/平台 URL 派生结果或浏览器 hash 不等于机器锁时发布失败。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.38）
- **OPS-OFFLINE-001 —** 每版 **MUST** 发布一个含四镜像完整 amd64+arm64 OCI index、Chart、Compose、Release manifest 和内部验证材料的离线 `.tar.zst`；归档自身签名与 Sigstore bundle **MUST** 位于外部 sidecar，**MUST NOT** 放入归档形成哈希自引用。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.39 B）
- **OPS-OFFLINE-002 —** `quoin-deploy compose|helm install --offline-archive <path>` **MUST** 先离线验证归档及外部 Sigstore bundle，再使用标准 OCI 工具把全部 index 复制到目标 registry 并保持 digest，逐项读取 index/per-platform digest 后才进入同一 install 状态机；任何值不等于 Release manifest 时 **MUST** 停止部署。离线模式是 `install` 的输入来源，**MUST NOT** 增加第二套安装流程或隐藏动词。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.39 B）

## 11. 协调升级与回滚边界

- **OPS-UPGRADE-001 —** 四个 OCI 镜像 **MUST** 由一个 Release 统一决定，组件 `release_version` **MUST** 严格相等；第一版 **MUST NOT** 承诺 N/N-1 在线滚动兼容。SemVer tag **MUST** 只作人类识别，运行清单 **MUST** 使用 manifest digest。（来源：[RUNTIME-CTRL-003](runtime-protocol.md#3-连接与握手runtimecontrolconnect)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.9）
- **OPS-UPGRADE-002 —** 升级向导 **MUST** 指示已登录 Admin 在 Web UI 执行 `prepareUpgrade`、查看确定性清单并仅由 Admin 通过 `upgrade-drain` 明确取消剩余 active task/browser operation；helper **MUST NOT** 接收 Web 凭据或调用产品 HTTP 写接口，只通过 OPS-VERIFY-003 同类的 Kubernetes verifier Job 或 Compose verifier service 轮询不对宿主公开的无认证 ops 指标 `quoin_upgrade_prepared`。Quoin 原子进入 Upgrade maintenance、停止新人工任务/调度并在活动工作清零后自动创建和完整验证升级前 Backup Run；只有该维护 revision 的全部项目 Safe 且升级备份 succeeded 时该 gauge 才为 1。观察到 1 后向导才可停止 Stele、Plinth、Lintel 与旧 Quoin，并 **MUST** 用同一 Quoin 镜像离线读取 SQLite 再验证 maintenance reason、revision、全部 Safe 与备份 digest 后继续；随后用新 Quoin 独占 data 执行前向 migration，Quoin Ready 后启动同版本 Plinth、Lintel、Stele。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.10）
- **OPS-UPGRADE-003 —** migration 完成前 Quoin **MUST NOT** Ready；版本不匹配的 Runtime/Stele **MUST** not ready、不领任务且不接收正式告警。维护期间错过调度 **MUST** 记录 RuntimeUnavailable 且 **MUST NOT** 补跑。（来源：[RUNTIME-AUTH-004](runtime-protocol.md#2-身份与认证)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.10）
- **OPS-UPGRADE-004 —** 每个 Release **MUST** 为 linux/amd64 与 linux/arm64 各附一个相同源码、相同命令契约的 `quoin-deploy` 单文件资产；其 `compose install|upgrade|backup|restore|verify` 与 `helm install|upgrade|backup|restore|verify` 子命令分别复用 `docker compose` 或操作者已有 `helm`/`kubectl` 权限，机械执行并持续显示阶段/真实检查结果。向导只在 active task 是否取消、恢复/回滚和不可替代的部署输入处询问，**MUST NOT** 用 Helm hook/启动 hook 隐式 migration 或取消任务；命令失败必须保留已完成阶段和可重试下一步。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.10/Q17.34）
- **OPS-UPGRADE-005 —** 新版本接受新写入前 **MAY** 恢复升级前备份并回旧版本；接受新写入后 **MUST NOT** 只回滚镜像，回退 **MUST** 显式恢复升级前备份。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.10）
- **OPS-UPGRADE-006 —** Git **MUST** 只保存版本化声明式 seed scenario 与期望断言，**MUST NOT** 提交人工制作的 SQLite/PVC 二进制。首版只验 fresh install；之后每版 **MUST** 从上一正式 Release manifest 获取真实 digest，启动 N-1 并经公开 HTTP/Runtime 路径创建用户、连接、告警、Attempt、Artifact、知识和成功备份，再验证 N-1→N 的 Compose/Helm 协调升级、migration、恢复及接受新写入前回滚；生成数据 **MUST** 只作该次 CI 证据。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.43）

## 12. Compose 与 Helm 包装要求

- **OPS-COMPOSE-001 —** 四服务 **MUST** 使用 `restart: unless-stopped`；Plinth、Lintel、Stele **MAY** 用 `depends_on: quoin: condition: service_healthy` 改善首次启动顺序，但运行期 Quoin 重启 **MUST** 只依赖各组件自己的重连与 Ready，**MUST NOT** 用 Compose `restart: true` 隐式传播全栈重启。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.32）
- **OPS-COMPOSE-002 —** 完整版本升级 **MUST** 只走协调升级向导，状态目录应用锁 **MUST** 继续作为 Compose 容器重建可能重叠时的最终裁决。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.32）
- **OPS-HELM-001 —** Chart **MUST** 使用 `Recreate`、固定安全上下文、固定内部端口、明确 PVC access mode、60 秒 termination grace 和由探针测试拥有的 probe 数值；这些核心边界 **MUST NOT** 暴露为可关闭的普通 values。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.12–Q17.15、Q17.29、Q17.42）

- **OPS-HELPER-001 —** 每版 **MUST** 为 `linux/amd64` 与 `linux/arm64` 分别发布静态 `quoin-deploy`；Release manifest **MUST** 记录两个资产名、SHA-256 与外部 Sigstore bundle 名。helper **MUST** 以 `quoin-deploy compose|helm <command> [--config <path>] [--report <path>]` 调用，`command` 封闭为 `install|upgrade|backup|restore|verify`；不得按宿主架构之外的条件下载或选择另一个 helper。（来源：Issue #17 Q17.10/Q17.34）
- **OPS-HELPER-002 —** helper **MUST** 只消费 Release manifest、经 `deployment-config.schema.json` 校验的最少输入与操作者本机现有 `docker compose` 或 `helm`/`kubectl`；下载、签名验证、配置渲染、preflight、平台执行和 post-verify **MUST** 使用可恢复阶段并把 last completed stage 写入本机临时 state file。相同 `release_version + backend + config digest + command` 重试 **MUST** 从已验证阶段继续；输入或目标状态变化 **MUST** 拒绝复用旧 state。（来源：Issue #17 Q17.10/Q17.33）
- **OPS-HELPER-003 —** helper 成功 **MUST** 退出 `0`；输入/Schema/签名/摘要/preflight 错误 **MUST** 退出 `2` 且不产生部署副作用；平台命令或行为验证失败 **MUST** 退出 `1`，保留原始外部命令 exit code、stdout/stderr 日志位置与稳定失败 code。所有路径 **MUST** 以原子 rename 写出 `verification-report.json`，至少包含 release/source commit、backend、architecture、command、每阶段状态、执行命令、原始 exit code、开始/结束时间、检查项及恢复动作；秘密与 attached-stdin 内容 **MUST NOT** 进入 report/state/log。（来源：Issue #17 Q17.10/Q17.33）
- **OPS-HELPER-004 —** `install|upgrade|backup|restore` **MUST** 在领域动作后调用同一 `verify` 检查器，并按该动作的封闭期望后状态裁决；失败 **MUST NOT** 自动删除成功创建的 PVC/volume/Secret 或回滚已提交 migration，而是保持最小安全状态并输出下一条可重试动作。恢复子命令成功后 helper **MUST** 先单独启动 Quoin、等待其以 maintenance Ready，再启动其余同版本组件并执行 `post-restore` verifier；该期望 **MUST** 是：Quoin 可提供 maintenance-safe API，`/readyz` 为 200 且 `mode=maintenance`/`acceptingWork=false`/`reason=maintenance`，全部 Runtime slot 为 revoked 且无 active Runtime，外部连接凭据为待重校验，同时 DB/Artifact/manifest/checksum/root-key binding 通过；这些预期隔离状态不得按 normal-mode Runtime 离线报失败，任何额外或缺失降级仍须 exit `1`。`verify` **MUST** 是只读且可重复执行；除 Kubernetes verifier Job/Compose verifier service 这一临时检查资源外，不得创建产品领域状态。（来源：Issue #17 Q17.10/Q17.33）

## 13. 验证门与证据边界

- **OPS-VERIFY-001 —** CI **MUST** 在一次性真实 Docker Compose 环境和真实 Kubernetes 测试集群（kind 或等价）分别完成安装与运行验收，**MUST NOT** 用 template/lint/build 代替实际启动和行为验证。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.33）
- **OPS-VERIFY-002 —** 原生 amd64 与原生 arm64 的最小矩阵 **MUST** 各自覆盖：四镜像按多平台 index digest 启动；探针与 metrics scrape；首次自动秘密引导及既有数据缺秘密 fail-closed；秘密→Admin→长期 workload 启动门（含 Admin Job 失败/重试且长期 workload 从未提前启动）；首次 Admin 登录；Plinth/Lintel 通过 attached stdin 一次性注册并在替换后拒绝旧长期 token；Plinth Bash/固定工具目录与 Landlock/seccomp 对抗自检；Lintel 真浏览器/noVNC/身份卷/trace；Stele Delivery；含 Artifact 的成功备份、helper 不持有 Web 凭据的 Admin UI 触发 + ops 指标观测路径与不可达时离线 fallback；停机恢复；post-restore verify 把 maintenance + 全 Runtime revoked + 连接待重校验识别为唯一预期隔离而不是普通失败；恢复后的 Session/Runtime/告警凭据失效；从上一 Release 动态造数后的升级与接受新写入前回滚；复用既有卷的服务重建；SIGTERM；存储故障；sentinel 泄漏扫描。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.33、Q17.34、Q17.43）
- **OPS-VERIFY-003 —** 发布门 **MUST** 实际验证离线归档签名、解包、registry 导入和 digest 读回。`quoin-deploy ... verify` **MUST** 校验 Release manifest 与 Sigstore subject、实际 workload image digest/版本、配置 Schema、固定副本/端口/安全上下文/卷、`/livez`/`/readyz`/`/metrics`、Runtime 注册/版本与存储探测；Kubernetes 路径在需要集群内访问时 **MUST** 创建同 Release verifier Job，Compose 路径 **MUST** 创建同 network 一次性 verifier service，均不得持有产品用户或外部连接凭据。输出必须是可保存的结构化检查清单，失败项带稳定 code 和恢复动作。Helm lint/schema、Compose config、OpenAPI/SQL/Proto/JSON Schema 校验 **MUST** 继续作为低层门禁，但其成功 **MUST NOT** 被报告为真实安装、恢复、升级或双架构运行通过。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.10/Q17.33/Q17.39）
- **OPS-VERIFY-004 —** 机器契约一致性 fixture **MUST** 至少证明：Helm/Compose 有效最少输入通过且遗漏必填/多余字段/禁配核心字段失败；组件生成 config 与 SQLite/Admin 字段零重叠；Chart/Compose 投影等于 Schema/Release manifest，helper 投影固定 retained PVC 而 Chart 渲染结果不含 PVC 对象且只引用固定 claim name；metrics 的 OpenAPI/SQL/Proto 外部枚举与目录引用集合严格相等且目录自有值带 authority；Plinth 镜像内 Debian package/path/version 等于工具目录；基础镜像、Playwright tag 源码、按平台派生的 Chromium URL 与实际 digest/hash 等于 release input lock；Backup Run 状态机拒绝非法跃迁、双 active、重复 scheduled boundary、在线/离线 actor 组合、终态改写与 DELETE；Release manifest 接受带 registry hostname/port 的 repository、拒绝缺失镜像/helper 平台或资产哈希、接受 SemVer prerelease/build asset 名并包含结构化验收摘要；`readiness-response.schema.json` 拒绝未知 reason 与字段关系冲突；每个外部 Sigstore bundle 的 subject 等于 manifest 中对应对象 digest 或实际 blob SHA-256。（来源：[SPEC-AUTHORITY-003](README.md#权威源与事实所有权)、[Issue #17](https://github.com/Suknna/quoin/issues/17)）

# Quoin v1 运维与部署规格

**状态：Draft**

**Non-normative：** 本文件（CATEGORY=`OPS`）承载 Quoin v1 的 普通 Kubernetes YAML、Compose、进程配置、容器镜像、卷与锁、健康检查、可观测性、备份恢复包装、发布供应链、离线分发、升级与部署验收语义。HTTP 路由与字段由 [`contracts/openapi.yaml`](contracts/openapi.yaml) 拥有，SQLite 字段与约束由 [`contracts/sql/schema.sql`](contracts/sql/schema.sql) 拥有，Runtime wire 枚举由 [`contracts/runtime.proto`](contracts/runtime.proto) 拥有，Quoin、Plinth、Lintel、Stele 的非秘密进程配置形状由 [`contracts/schemas/deployment-config.schema.json`](contracts/schemas/deployment-config.schema.json) 拥有；发布 manifest 形状由 [`contracts/schemas/release-manifest.schema.json`](contracts/schemas/release-manifest.schema.json) 拥有，自定义指标 family 由 [`contracts/metrics.yaml`](contracts/metrics.yaml) 拥有，Plinth worker 本地工具目录由 [`contracts/plinth-worker-tools.yaml`](contracts/plinth-worker-tools.yaml) 拥有。本文件不复制这些机器契约的完整字段或枚举。

## 1. 范围与事实所有权

- **OPS-SCOPE-001 —** Admin 可理解的运维设置（备份时间、IANA 时区、备份保留份数和生成型 Artifact 保留天数）**MUST** 只由 Admin Web UI 管理并持久化到 SQLite；部署配置 **MUST** 只保存 public Origin、卷与 Secret/file 路径、TLS 接入和少量不可由产品推导的基础设施事实，两类字段 **MUST NOT** 重叠。（来源：[CONTEXT「存储、保留与部署」](../../../CONTEXT.md#存储保留与部署)、[Issue #17](https://github.com/Suknna/quoin/issues/17)）
- **OPS-SCOPE-002 —** Kubernetes 是主要交付目标，部署工件 MUST 是可直接审阅、应用的普通 YAML，覆盖六个服务角色的 workload、Service、配置/Secret 引用及既有持久卷边界；MUST NOT 要求 Helm、Chart、values 或复杂生成器。Compose 是辅助交付，MUST 是可直接运行的简单文件，且不得要求先生成安装配置。（来源：[Issue #93](https://github.com/Suknna/quoin/issues/93)、ADR-0001）
- **OPS-SCOPE-003 —** `deployment-config.schema.json` 继续拥有各后端组件的非秘密进程配置；只有其旧 Helm/Compose 安装投影、Chart/values 和 Helm helper 已成为历史资产，不再是当前交付、发布或验收要求。历史证据不得被重写为已验证新拓扑。（来源：ADR-0001）
- **OPS-SCOPE-004 —** 部署配置 MUST NOT 拥有应用镜像版本、容器内部监听地址或端口、replica/HPA、Admin 运维设置、SQLite durability、Artifact GC 周期或 batch size；镜像 digest、固定内部端口和进程内部调优仍各自拥有。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.1/Q17.22/Q17.42）

## 2. 进程配置与投影

- **OPS-CONFIG-001 —** 每个组件只接受固定、最小的 YAML 进程配置或只读 Secret 文件引用；配置在启动时读取一次并在进程生命周期内不可变。变更 MUST 通过显式重启生效，v1 MUST NOT 提供 watcher 或 `SIGHUP` reload。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.1）
- **OPS-CONFIG-002 —** Secret、根密钥、服务 token 与私钥 MUST 只以独立只读文件路径出现在配置中；配置、Kubernetes YAML、Compose 文件和前端产物 MUST NOT 承载 secret value。实现不得为同一配置字段另建同义环境变量或 CLI flag。（来源：[SEC-KEY-001](security.md#5-根密钥与可逆连接秘密)）
- **OPS-CONFIG-003 —** Admin Web UI + SQLite 设置 MUST 按其领域命令即时生效且不依赖进程配置 reload。普通 Kubernetes YAML 与 Compose 只投影组件实际消费的最少配置，不得建立第二份用户可编辑配置模型。（来源：[Issue #93](https://github.com/Suknna/quoin/issues/93)）
- **OPS-PACKAGE-001 —** Kubernetes YAML 与 Compose bundle MUST 是可独立部署的完整投影：包括入口 Caddy、前端静态服务、Quoin、Plinth、Lintel、Stele 的 workload/service、既有 volume/security/probe 配置和必要 Secret 引用。不得将实现留给未定义人工步骤。（来源：[Issue #93](https://github.com/Suknna/quoin/issues/93)、ADR-0001）
- **OPS-PACKAGE-002 —** 旧 Helm 专用 bootstrap、retained PVC、Chart lookup 与 `quoin-deploy helm` 流程已由 ADR-0001 替换；当前安装在不削弱既有秘密、数据卷和 Admin bootstrap 边界的前提下，以普通 Kubernetes YAML 或简单 Compose 提供。（来源：ADR-0001）

## 3. 网络、TLS 与固定端口

- **OPS-NET-001 —** Quoin MUST NOT 签发公共证书。入口 Caddy MUST 加载部署者提供的 Kubernetes TLS Secret（Compose 对应只读证书文件）并终止 TLS；不要求 Ingress Controller、cert-manager、ACME 或公网证书。public Origin MUST 显式配置且 MUST NOT 从 `Host`/`Forwarded` 临时推导。（来源：[SEC-CSRF-003](security.md#3-session同源请求与浏览器响应)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.5）
- **OPS-NET-002 —** 容器内部端口 **MUST** 固定为：Quoin public HTTP `8080`、Quoin Runtime gRPC `8443`、四个后端组件 ops `9090`、Stele webhook 在自身容器使用 `8080`；进程配置 **MUST NOT** 改写内部 host/port，只有 Compose host publish 与 Kubernetes Service 外部映射 **MAY** 配置。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.30、Q17.42）
- **OPS-NET-003 —** Kubernetes YAML MUST 为入口 Caddy、前端、Quoin public、Quoin Runtime gRPC、Stele webhook 和后端组件 ops 建立职责分离的 Service；Plinth/Lintel MUST NOT 创建业务入站 Service，Runtime 与 ops MUST NOT 进入公共入口。入口 Caddy 的标准 Service 暴露类型由目标集群网络条件选择，不假定 LoadBalancer。（来源：[CONTEXT「服务暴露拓扑」](../../../CONTEXT.md#存储保留与部署)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.30）
- **OPS-NET-004 —** Compose MUST 提供入口 Caddy、前端、Quoin、Plinth、Lintel、Stele 六个服务；默认只由 Caddy publish 公共端口，Quoin public、Stele webhook、Runtime 与全部 ops MUST 只在内部 network 暴露。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.30）

## 4. 运维端点、探针与关停

- **OPS-HEALTH-001 —** Quoin、Plinth、Lintel、Stele 四个后端组件 MUST 在独立 ops listener 提供 `/livez`、`/readyz` 与 `/metrics`；这些端点 MUST NOT 进入产品 OpenAPI，也 MUST NOT 实现应用层认证。普通 Kubernetes YAML 不强制 Prometheus Operator、ServiceMonitor/PodMonitor 或部署专属 NetworkPolicy。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.6）
- **OPS-HEALTH-002 —** `/livez` **MUST** 只判断本进程能否继续推进且不存在本地不可恢复 fatal state，**MUST NOT** 依赖 Quoin peer、外部系统、maintenance 或磁盘余量；`startupProbe` **MUST** 只等待 ops listener 启动。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.14）
- **OPS-HEALTH-003 —** `/readyz` **MUST** 判断组件能否承担其职责并返回由 `$id=https://github.com/Suknna/quoin/schemas/readiness-response.schema.json`（`contracts/schemas/readiness-response.schema.json`）唯一拥有字段、枚举与字段关系的固定 JSON；Ready 返回 200，not ready 返回 503。响应 **MUST NOT** 返回动态错误文本或新增机器契约未登记的 reason。探针 period、timeout 与 failure threshold **MUST** 由打包清单拥有并经慢 migration/慢启动测试，**MUST NOT** 成为用户设置。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.13、Q17.14）
- **OPS-HEALTH-004 —** Quoin 在取得数据目录锁并完成 migration 前 **MUST NOT** Ready；migration 完成且 maintenance-safe API 可用后，即使仍处于 maintenance，`/readyz` **MUST** 返回 200 并声明 `mode=maintenance`、`acceptingWork=false`，普通工作仍由维护门禁拒绝。（来源：[HTTP-MAINT-001](http-api.md#31-维护隔离)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.13）
- **OPS-HEALTH-005 —** Plinth/Lintel 只有在 token、严格 Proto 契约指纹握手和控制流被 Quoin 接受后才 **MUST** Ready；Stele 只有在 Proto 契约指纹握手与告警源 credential digest snapshot 加载成功后才 **MUST** Ready。Quoin 暂时离线时 Runtime **MUST** 保持 live 但 not ready，且 **MUST NOT** 因 peer 离线触发循环重启。（来源：[RUNTIME-AUTH-004](runtime-protocol.md#2-身份与认证)、[RUNTIME-CTRL-003](runtime-protocol.md#3-连接与握手runtimecontrolconnect)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.13）
- **OPS-HEALTH-006 —** `/livez` **MUST** 在 healthy 时返回 HTTP 200 与固定 `text/plain; charset=utf-8` 正文 `ok\n`，本地不可恢复 fatal state 返回 HTTP 500 与固定正文 `fatal\n`；`/metrics` **MUST** 使用 Prometheus text exposition content type。收到 SIGTERM 后，`/readyz` **MUST** 立即返回 503、`reason=draining`、`acceptingWork=false`，但 `/livez` 在进程仍能执行关停收口时继续返回 200；进程退出后由连接失败表达停止，**MUST NOT** 在退出前伪造 fatal。（来源：Issue #17 Q17.13/Q17.14/Q17.29）
- **OPS-SHUTDOWN-001 —** Kubernetes `terminationGracePeriodSeconds` 与 Compose `stop_grace_period` **MUST** 均为 60 秒；SIGTERM 后组件 **MUST** 立即停止新准入，最多使用前 45 秒完成当前 SQLite 事务、Artifact 原子发布、in-flight HTTP/Stele 请求、Runtime GoAway/结果确认和 Browser stop/incomplete trace 收口，并至少保留 15 秒关闭连接和退出。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.29）
- **OPS-SHUTDOWN-002 —** 关停 **MUST NOT** 等待任意长模型或浏览器工作自然完成，也 **MUST NOT** 把未完成工作伪装为 Cancelled/Success；实现 **MUST** 复用既有 fence/reconcile 语义。清单 **MUST NOT** 使用 sleep 型 preStop hook，核心关停 **MUST** 由幂等 SIGTERM handler 实现。（来源：[RUNTIME-TASK-004](runtime-protocol.md#4-任务派发与调和)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.29）

## 5. 拓扑、卷与进程锁

- **OPS-TOPOLOGY-001 —** 第一版 **MUST** 固定 Quoin、Plinth、Lintel、Stele 各一个 active replica，Kubernetes YAML 与 Compose **MUST** 使用零重叠替换，Kubernetes Deployment **MUST** 使用 `Recreate`；第一版 **MUST NOT** 提供 replicas 或 HPA 配置。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.12）
- **OPS-TOPOLOGY-002 —** Quoin、Plinth、Lintel **MUST** 分别在 `quoin-data`、`plinth-state`、`lintel-state` 固定 lock file 上取得非阻塞内核 advisory exclusive lock并持有文件描述符到退出；锁失败 **MUST** 立即以稳定错误码退出，lock file **MUST NOT** 被当作 PID 权威或通过删除“陈旧 PID”绕过。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.12）
- **OPS-TOPOLOGY-003 —** Quoin 服务、migration、restore 与 root-key rebind **MUST** 争用同一个 `quoin-data` 锁。SQLite WAL 数据卷 **MUST** 使用本地或块存储且 **MUST NOT** 使用 NFS/SMB；CSI 支持时 **SHOULD** 使用 `ReadWriteOncePod`，否则 **MUST** 使用 `ReadWriteOnce + Recreate + 应用锁`。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.12）
- **OPS-STORAGE-001 —** `quoin-data` **MUST** 同卷保存 SQLite、Artifact staging 与最终文件以满足 [DATA-ARTIFACT-001](persistence.md#16-artifact-与保留) 的同文件系统原子 rename；`quoin-backup` **MUST** 是独立卷，`plinth-state` 与 `lintel-state` **MUST** 各自独立，Stele **MUST NOT** 挂载持久卷。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.3）
- **OPS-STORAGE-002 —** 只有 Attempt workspace、普通 `/tmp` 与 Lintel 专用 `/dev/shm` **MAY** 使用可丢弃卷；Lintel `/dev/shm` **MUST** 使用 memory-backed emptyDir/tmpfs，Kubernetes YAML 与 Compose 均默认 1 GiB，并将该下限直接提供给 Lintel `minimumShmBytes`。Lintel 启动时 **MUST** 验证 `/dev/shm` 可写且实测总容量不小于 `minimumShmBytes`，不满足时 fail closed；**MUST NOT** 静默使用 `--disable-dev-shm-usage` 回退普通 `/tmp`。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.31）
- **OPS-STORAGE-003 —** 第一版 **MUST NOT** 默认设置 CPU/内存 limits；Kubernetes YAML requests/limits MAY 显式提供且默认空。Kubernetes PVC 容量 **MUST** 由部署操作者显式填写；Compose named volume **MUST NOT** 施加应用层容量限制。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.11）
- **OPS-STORAGE-004 —** 已知大小的 Artifact/备份操作 **MUST** 对目标目录和所需字节执行精确 preflight；`ENOSPC`、`EDQUOT`、`EROFS` 或持久化 fsync/rename 失败 **MUST** 把对应 storage health 置为不可写、令 Quoin not ready 并在 SQLite 仍可写时把当前领域任务或 Backup Run 持久化为稳定失败。恢复 **MUST** 在同一目录通过 create→write→fsync→rename→父目录 fsync→unlink probe 和当前操作 preflight，且 **MUST NOT** 依赖统一剩余百分比、静默删历史、隐藏预留文件或自动扩容。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.28）

## 6. 备份、恢复与 Artifact GC

- **OPS-BACKUP-001 —** `backups` **MUST** 是状态为 `queued|running|succeeded|failed` 的受限状态机聚合，只允许前向迁移，终态后不可修改，任何状态均禁止 DELETE；任一时刻最多一个 active Backup Run。具体字段、CHECK、索引与触发器只由 `contracts/sql/schema.sql` 拥有。（来源：[DATA-BACKUP-007](persistence.md#17-备份与恢复)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.21）
- **OPS-BACKUP-002 —** `triggerBackup` **MUST** 先持久化 active row 再返回 202；同一 `client_command_id` 重试 **MUST** 返回同一 row，其他手动触发 **MUST** 返回带 active ID 的冲突，定时触发 **MUST** 与 active run 合并而不排队第二份。启动时先按 OPS-BACKUP-003 收敛上一进程遗留 active row；随后调度器只在 normal mode、storage writable 且不存在 active run 时，按 `backups.scheduled_for` 中最后已观察 UTC 计划边界（无行时按 `contracts/sql/schema.sql#backup_settings.schedule_enabled_at` 的备份设置启用时间）计算停机期间错过的触发，并最多为最新边界创建一份 `trigger_kind=scheduled`、`execution_mode=online` Run；`scheduled_for` 唯一索引 **MUST** 使该边界的重试或并发启动只能命中原行，完成这一轮 catch-up 判定后才开放下一次正常计划触发。第一版 **MUST NOT** 提供取消备份。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.21）
- **OPS-BACKUP-003 —** Quoin 启动时 **MUST** 在开放新触发前把上一进程遗留的 `queued|running` 行收敛为 `failed`，记录稳定进程中断错误码与结束时间；失败 **MUST NOT** 删除旧成功备份，后续正常周期 **MUST** 继续。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.21）
- **OPS-BACKUP-004 —** 备份执行、manifest/checksum 门禁、Artifact 精确集合、目录 fsync、恢复后信任重建与敏感下载 **MUST** 分别遵守 [DATA-BACKUP-001..007](persistence.md#17-备份与恢复)、[SEC-RESTORE-001..004](security.md#9-备份恢复维护与信任重建) 与 [HTTP-FILE-006](http-api.md#9-上传与下载)；`integrity_check` **MUST NOT** 替代已完整发布的 manifest+checksum。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.4、Q17.8）
- **OPS-BACKUP-005 —** `queued→running` **MUST** 进入 preflight，`queued→failed` **MUST** 保持 queued，`running→failed` **MUST** 保持失败前 stage，只有 manifest_publish **MAY** 进入 succeeded；失败行 **MUST** 携带稳定 `error_code`、`retryable` 和有界详情。无标签 gauge `quoin_backup_active` 必须按是否存在 `queued|running` 行精确投影为 0 或 1，`quoin_backup_last_success_timestamp_seconds` 只按最后 succeeded run 投影，`quoin_backup_last_online_manual_success_timestamp_seconds` 只按 `trigger_kind=manual AND execution_mode=online` 的最后 succeeded run 投影；告警规则不得查询不存在的通用 last-success 指标。（来源：Issue #17 Q17.21/Q17.27）
- **OPS-BACKUP-006 —** Quoin 可达时，在线备份 MUST 由已登录 Admin 在 Web UI 发起；Kubernetes 部署者可用普通 `kubectl` 观察不公开的 ops 指标，Compose 可使用现有 `quoin-deploy compose backup` 辅助路径。两者都必须先要求 `quoin_accepting_work=1`、全部 `quoin_maintenance` series 为 0 并有界等待 `quoin_backup_active=0`；任一前提不满足或等待超时必须以稳定 `online_backup_unavailable` 错误停止，提示操作者退出维护/等待现有备份后重试。满足前提后记录 `process_start_time_seconds`、`quoin_backup_last_online_manual_success_timestamp_seconds` 与 `quoin_backup_failures_total` 的基线，立即指示已登录 Admin 在 Web UI 执行“立即备份”，并只轮询 `/metrics`；helper **MUST NOT** 接收账号、密码或 Session，也 **MUST NOT** 调用产品 HTTP 写接口。观察到 online-manual last-success 严格增加且 active=0 即成功（允许一次 scrape 间隔内完成而未观测到 active=1）；若曾观察到 active=1 后归零而该时间未增加、failure counter 增加或等待超时即失败；等待期间 `quoin_accepting_work` 变为 0、任一 `quoin_maintenance` series 变为 1，或 `process_start_time_seconds` 改变且未观察到新成功时，必须以稳定 observation-reset 错误停止并要求重试，不得跨进程拼接 counter。只有 Quoin 不可达时，操作者才可显式选择离线 fallback。fallback **MUST** 先停止全部 workload 并证明 `quoin-data` 锁空闲，再以同一 Release Quoin 镜像挂载同一 data/backup/root-key 运行 `quoin backup --offline`；子命令取得同一 data lock、创建并推进同一 `backups` 聚合、执行 [DATA-BACKUP-001..007](persistence.md#17-备份与恢复) 的 SQLite/Artifact/manifest/checksum/fsync 流程，并固定记录 `trigger_kind=manual`、`execution_mode=offline`、`triggered_by=NULL`；Web 手动、计划与升级前备份固定为 `execution_mode=online`，只有在线手动/升级行引用真实 User。失败必须持久化稳定 stage/error、保持旧成功备份与 data 不变并保持 workload 停止；操作者可重跑同一操作，或在该次失败恢复提示中明确选择重新启动原 digest 的 unchanged workload；**MUST NOT** 另建第二种备份格式。（来源：Issue #17 Q17.10、Q17.21）
- **OPS-RESTORE-001 —** 恢复 **MUST** 复用同一 Release 的 Quoin 镜像和 `quoin restore` 子命令；普通 Kubernetes YAML MUST 用一次性 Pod/Job 包装，Compose **MUST** 用 `docker compose run --rm` 包装，且 **MUST NOT** 要求宿主安装第二套 Quoin CLI 或维护独立 restore 镜像。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.4）
- **OPS-RESTORE-002 —** Kubernetes 部署者 MUST 通过普通 `kubectl` 停止工作负载并运行挂载 data、backup 与根密钥的同 Release Quoin 一次性 Job；Compose 可使用现有 `quoin-deploy compose restore` 辅助路径。两种路径均须先显示目标 manifest 摘要并取得一次真实确认，再执行离线恢复；恢复权限属于拥有 PVC/目录和根密钥访问权的部署操作者，**MUST NOT** 从 Web Admin Session 推导。TTY **MAY** 只承担目标选择、确认、恢复 Admin 选择与临时密码一次显示；失败必须保留原 data 回滚点和明确的可重试阶段。（来源：[SEC-RESTORE-004](security.md#9-备份恢复维护与信任重建)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.4）
- **OPS-GC-001 —** 唯一 Quoin 进程内 **MUST** 只有一个 artifact-storage coordinator；备份从快照枚举到复制完成期间 **MUST** 独占，GC **MUST** 使用有界小批次并在备份到达时完成当前批次后让出。第一版 **MUST NOT** 增加 SQLite lease、独立 GC 进程或 sidecar。（来源：[DATA-ARTIFACT-004](persistence.md#16-artifact-与保留)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.22）
- **OPS-GC-002 —** GC **MUST** 在启动后与固定内部周期唤醒，并在健康运行时保证到期对象 24 小时内处理；周期与 batch size **MUST** 是进程内部调优，**MUST NOT** 进入 Admin 或部署配置。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.22）

## 7. 镜像、架构与 worker 工具

- **OPS-IMAGE-003 —** Quoin 与 Stele **MUST** 使用 `contracts/release-inputs.yaml` 锁定的 Debian 13 distroless `static-debian13:nonroot` index/per-platform digest；若真实动态链接审计证明必须升级到 `base/cc`，必须先修改 release input lock 与本条款并重跑双架构验收，不得在构建逻辑中保留条件选择。Plinth 与 Lintel **MUST** 使用同一锁中 digest-pinned Debian 13 slim；Plinth 提供真实 `/bin/bash` 与固定工具集，Lintel 构建 browser runtime。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.35 D）
- **OPS-IMAGE-004 —** `contracts/plinth-worker-tools.yaml` **MUST** 是 Plinth worker 的 Bash 启动 argv、本地命令、绝对路径、要求版本、双架构工件与 Landlock 只读运行时路径的唯一机器目录；Plinth 构建 **MUST** 直接消费该目录，**MUST NOT** 在另一锁文件手工复制工具版本。（来源：[ARCH-WORKER-003](architecture.md#4-plinth-supervisor--worker-边界)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.35 D）
- **OPS-IMAGE-005 —** Bash Tool **MUST** 由 worker 以清空后的环境、当前 Attempt 工作区 cwd 和目录声明的 `/bin/bash --noprofile --norc -c` argv 真实执行；shell 的存在 **MUST NOT** 被当作安全边界，边界仍由无凭据 worker、[ARCH-WORKER-004](architecture.md#4-plinth-supervisor--worker-边界) 的 Landlock/seccomp 和启动对抗自检承担。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.35 D）
- **OPS-IMAGE-006 —** 所有 base 与 browser artifact **MUST** 在 `contracts/release-inputs.yaml` 锁 index/per-platform digest 或每架构 SHA-256；Plinth 直接安装的 OS package **MUST** 在 `contracts/plinth-worker-tools.yaml` 锁完整 Debian version，Lintel 的 Playwright Debian 13 browser/native-deps 包集合、x11vnc 与每架构完整 Debian version **MUST** 在 `release-inputs.yaml` 锁定。构建器 **MUST** 以 digest-pinned base、`--no-install-recommends` 和逐包 `name=version` 安装，验证实际已安装版本及关键 executable；更新 **MUST** 作为独立依赖变化通过双架构完整验收。容器启动时 **MUST NOT** 安装或下载软件。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.35 D）

## 8. 容器安全边界与首次秘密引导

- **OPS-CONTAINER-001 —** 五个应用镜像（Quoin、Plinth、Lintel、Stele、前端） **MUST** 使用固定非 root UID/GID；Kubernetes **MUST** 设置 `runAsNonRoot=true`、`allowPrivilegeEscalation=false`、只读 root filesystem、drop `ALL` capabilities 与 `seccompProfile=RuntimeDefault`，持久卷 **MUST** 使用匹配 `fsGroup` 与 `fsGroupChangePolicy=OnRootMismatch`。普通 Kubernetes YAML MUST NOT 提供关闭这些边界的替代配置。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.15）
- **OPS-CONTAINER-002 —** 四个后端正常运行 Pod MUST 设置 `automountServiceAccountToken=false`，普通 Kubernetes YAML MUST NOT 创建业务 RBAC；Plinth Kubernetes 工具仍 MUST 只消费 Quoin 下发的连接凭据，restore/upgrade MUST 复用部署操作者已有 kubectl 权限。（来源：[ARCH-WORKER-002](architecture.md#4-plinth-supervisor--worker-边界)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.17）
- **OPS-CONTAINER-003 —** Lintel **MUST** 固定以 `--no-sandbox` 启动 Chromium，第一版 **MUST NOT** 要求 user-namespace sandbox、sandbox self-test 或 setuid sandbox，也 **MUST NOT** 把该参数作为探测失败后的临时降级；剩余隔离只由非 root 容器、只读 root filesystem、capability/seccomp、专用身份卷和基础设施网络边界承担。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.16 C）
- **OPS-SECRET-001 —** 第一版 **MUST** 在空白首次安装自动生成 32-byte 根密钥、32-byte Stele service token 与部署私有内部 TLS CA/server certificate；Quoin 与 Stele **MUST** 只读挂载同一 Stele token 文件。引导 **MUST** 在既有 data claim/SQLite/Artifact/引导标记存在而秘密缺失、部分存在或无效时 fail closed；升级 **MUST NOT** 自动重建秘密。（来源：[SEC-KEY-001..002](security.md#5-根密钥与可逆连接秘密)、[SEC-KEY-009](security.md#5-根密钥与可逆连接秘密)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.40 B）
- **OPS-SECRET-002 —** 普通 Kubernetes YAML MUST 使用同一 Quoin 镜像的一次性 bootstrap Job，并引用由部署者提供或受控创建的固定名称 Secret。短生命周期 ServiceAccount/Role 如确有必要，只允许读取和更新该确定名称，Job 完成后 MUST 删除，正常 Pod 仍 MUST 无 token/RBAC。该秘密 bootstrap Job **MUST** 先于 OPS-PACKAGE-003 的 Admin bootstrap Job 完成；Secret 已写而数据库尚未建立的部分失败 **MUST** 在重试时复用该 Secret 且不得重新生成。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.40 B）
- **OPS-SECRET-003 —** Compose **MUST** 使用同一 Quoin 镜像的一次性 bootstrap service，以目录锁、`O_EXCL`、`0600`、文件与父目录 fsync 把秘密写入部署目录外的独立目录，正常容器 **MUST** 只读挂载。已有 Secret/file **MAY** 直接复用，自动引导 **MUST NOT** 接管轮换。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.40 B）
- **OPS-SECRET-004 —** Kubernetes YAML 与 Compose MUST NOT 把 secret value 放入环境变量、发布记录、Release manifest 或日志；内部 TLS、Stele token 与根密钥的运行期读取仍 **MUST** 遵守 [SEC-KEY-001](security.md#5-根密钥与可逆连接秘密) 与 [SEC-SERVICE-001](security.md#4-权限与服务身份)。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.40 B）
- **OPS-RUNTIME-REG-001 —** Plinth/Lintel 正常服务 **MUST** 只从各自状态卷固定 `0600` 文件读取长期 token，**MUST NOT** 接受一次性注册令牌的配置字段、环境变量、argv 或 Kubernetes Secret。首次注册或替换 **MUST** 使用同一组件镜像的 `<component> runtime register --token-stdin --config /etc/quoin/<component>.yaml` 一次性子命令：从 attached stdin 读取恰好一个注册令牌且不回显，完成 [RUNTIME-REG-001..003](runtime-protocol.md#11-注册与轮换) 后以临时文件→`fsync`→原子 rename→父目录 `fsync` 写入长期 token，stdout/stderr **MUST NOT** 输出任一 token。（来源：[RUNTIME-AUTH-002](runtime-protocol.md#2-身份与认证)、[Issue #17](https://github.com/Suknna/quoin/issues/17) 部署闭环）
- **OPS-RUNTIME-REG-002 —** Kubernetes YAML/Compose 安装流程及状态卷丢失后的 Admin Web UI“替换 Runtime”流程 **MUST** 对每个 slot 依次停止目标 Runtime、证明状态卷锁空闲、创建挂载同一状态卷/配置/CA 的一次性 Pod 或 `docker compose run --rm` 容器、只通过 attached stdin 传入刚在 Web UI reveal 的 60 秒令牌、成功后删除一次性资源并启动正常单副本；失败时 **MUST** 保持该 Runtime 停止并要求重新签发令牌。令牌 **MUST NOT** 进入 YAML、shell argv/history、临时文件、Secret、Job/Pod annotation、部署记录或日志。（来源：[SEC-REVEAL-005](security.md#6-一次性秘密-reveal-与轮换)、[RUNTIME-REG-001](runtime-protocol.md#11-注册与轮换)）

## 9. 日志、指标与推荐告警

- **OPS-LOG-001 —** Quoin、Plinth、Lintel、Stele 四个后端组件 MUST 只向 stdout/stderr 输出 UTF-8 JSON Lines，**MUST NOT** 写或轮转容器内日志文件；固定字段至少包含 UTC timestamp、level、component、release、稳定 code 与 message，并 **MAY** 带非秘密 correlation ID。（来源：[SEC-LOG-001](security.md#7-审计错误与日志)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.19）
- **OPS-LOG-002 —** 日志、指标 label、审计、持久诊断和 UI 技术详情 **MUST** 只使用字段白名单，默认 **MUST NOT** 记录 body、headers、gRPC metadata、完整 URL query 或任意对象 dump；秘密类型 **MUST** 只输出固定 `[REDACTED]`，发布门 **MUST** 执行 sentinel 泄漏扫描。（来源：[SEC-LOG-001..003](security.md#7-审计错误与日志)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.19）
- **OPS-METRIC-001 —** `contracts/metrics.yaml` **MUST** 是四个后端组件的**自定义业务/运维** metric family 的唯一机器权威；每个 family **MUST** 声明 name、type、HELP、label names 和封闭 label values。Go runtime/process 等标准采集器 family 由对应上游 collector 拥有，**MUST NOT** 在本目录复制定义。已有 OpenAPI/SQL/Proto 枚举 **MUST** 通过稳定 symbol 引用和目录拥有的标准化投影规则消费，fixture **MUST** 从真实机器源解析并断言集合严格相等；目录自有值 **MUST** 标记 `authority: metrics`。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.23）
- **OPS-METRIC-002 —** HTTP 指标 **MUST** 只使用封闭 `route_group`、`method`、`status_class`，gRPC 指标 **MUST** 只使用封闭 `rpc_group` 与 canonical status code；完整 URL、path/query 值、用户、对象 ID、每个 OpenAPI operation 与动态错误文本 **MUST NOT** 成为 label。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.24）
- **OPS-METRIC-003 —** 每组件 **MUST** 从启动起导出无 label 的 `<component>_ready`；Quoin 另 **MUST** 导出无 label 的 `quoin_accepting_work`、引用 `maintenance_state.reason` 的 `quoin_maintenance`，以及仅在 Upgrade maintenance 当前 revision 全部 Safe 且升级前 Backup Run succeeded 时为 1 的无 label `quoin_upgrade_prepared`。所有预知 series **MUST** 启动即显式导出 0，精确 not-ready reason **MUST** 只进入 `/readyz` 固定 JSON 与 JSON 日志。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.25）
- **OPS-METRIC-004 —** `*_total` **MUST** 是允许进程重启归零的内存 counter，**MUST NOT** 扫描 SQLite 历史或增加指标持久表；active/in-progress/firing/slot/ready 等 gauge **MUST** 从当前 SQLite 或内存权威投影。第一版 latency **MUST** 只使用 classic histogram，桶 **MUST** 由真实原型与 SLO 固定且 **MUST NOT** 提供 native/classic 运行开关。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.26）
- **OPS-ALERT-001 —** 部署者 MAY 在其现有监控栈中声明由 `contracts/metrics.yaml` 校验的 `PrometheusRule`，至少覆盖：组件 not-ready 5 分钟、Quoin 不接工作 15 分钟、`quoin_backup_schedule_overdue == 1`、`quoin_backup_active == 1 and quoin_backup_oldest_active_age_seconds > 7200`、备份执行失败（`increase(quoin_backup_failures_total[15m]) > 0`）、Runtime 离线 5 分钟、stream queue overflow 在 5 分钟窗口增加、storage 不可写 1 分钟、Artifact GC 超过 24 小时未成功、Stele unavailable 5 分钟。规则中的全部 family 与 label/value **MUST** 由 metrics catalog 机械校验存在，**MUST NOT** 手写目录外指标名。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.27）
- **OPS-ALERT-002 —** 普通 Kubernetes YAML 与 Compose MUST NOT 创建 Grafana dashboard、通知器或 Alertmanager 路由，也 MUST NOT 强依赖 Prometheus Operator；通知与路由继续由部署者现有监控栈拥有。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.27）

## 10. Release manifest、供应链与离线分发

- **OPS-RELEASE-001 —** 每个 annotated SemVer tag MUST 产生 `release-manifest.json`。发布版本用于展示、审计和溯源；运行部署使用 digest，MUST NOT 使用 `latest`。manifest 必须记录五个应用镜像的独立版本与 index/per-platform digest、来源 commit、浏览器锁、Compose 资产、必要签名与结构化验收摘要；不得要求 Chart/OCI Chart 工件。（来源：[Issue #93](https://github.com/Suknna/quoin/issues/93)）
- **OPS-RELEASE-002 —** 任一 Proto 权威契约文件变化 MUST 重建 Quoin、Plinth、Lintel、Stele 和前端五个应用镜像；OpenAPI 契约变化 MUST 重建 Quoin 与前端。契约未变的局部实现变化 MAY 只重建受影响应用；固定版本第三方 Caddy 镜像不因业务契约变化重建。构建输入必须绑定统一 Proto 契约指纹，部署者不得以运行配置伪造产物契约身份。（来源：[Issue #93](https://github.com/Suknna/quoin/issues/93)、ADR-0001）
- **OPS-RELEASE-003 —** 供应链完整性、镜像 digest、SBOM、provenance 和 Sigstore 验证继续适用于当前发布资产；删除 Helm 不得移除仍适用的镜像/Compose/离线资产校验。历史 Chart 资产及其验证要求已被 ADR-0001 替换。（来源：ADR-0001）

## 11. 协调升级与回滚边界

- **OPS-UPGRADE-001 —** 五个应用镜像 MAY 使用独立发布版本；运行通信以统一 Proto 契约指纹而非发布版本相等为准。第一版 MUST NOT 承诺跨契约或 N/N-1 在线滚动兼容。SemVer tag 只作人类识别，运行清单使用 manifest digest。（来源：[RUNTIME-CTRL-003](runtime-protocol.md#3-连接与握手runtimecontrolconnect)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.9）
- **OPS-UPGRADE-002 —** 升级向导 **MUST** 指示已登录 Admin 在 Web UI 执行 `prepareUpgrade`、查看确定性清单并仅由 Admin 通过 `upgrade-drain` 明确取消剩余 active task/browser operation；helper **MUST NOT** 接收 Web 凭据或调用产品 HTTP 写接口，只通过 OPS-VERIFY-003 同类的 Kubernetes verifier Job 或 Compose verifier service 轮询不对宿主公开的无认证 ops 指标 `quoin_upgrade_prepared`。Quoin 原子进入 Upgrade maintenance、停止新人工任务/调度并在活动工作清零后自动创建和完整验证升级前 Backup Run；只有该维护 revision 的全部项目 Safe 且升级备份 succeeded 时该 gauge 才为 1。观察到 1 后向导才可停止 Stele、Plinth、Lintel 与旧 Quoin，并 **MUST** 用同一 Quoin 镜像离线读取 SQLite 再验证 maintenance reason、revision、全部 Safe 与备份 digest 后继续；随后用新 Quoin 独占 data 执行前向 migration，Quoin Ready 后启动与 Quoin 同一 Proto 契约指纹的 Plinth、Lintel、Stele。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.10）
- **OPS-UPGRADE-003 —** migration 完成前 Quoin **MUST NOT** Ready；版本不匹配的 Runtime/Stele **MUST** not ready、不领任务且不接收正式告警。维护期间错过调度 **MUST** 记录 RuntimeUnavailable 且 **MUST NOT** 补跑。（来源：[RUNTIME-AUTH-004](runtime-protocol.md#2-身份与认证)、[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.10）
- **OPS-UPGRADE-004 —** Compose MAY 使用现有 `quoin-deploy compose install|upgrade|backup|restore|verify|recover-lintel` 辅助命令。Kubernetes 生命周期不提供同名 helper DSL：部署者 MUST 以普通 `kubectl apply/delete/rollout` 管理清单，并在需要时运行同一 Release Quoin 镜像的一次性 `quoin admin create`、`quoin backup --offline`、`quoin restore`、`quoin migrate` 或 `quoin maintenance recover-lintel`。现有 `quoin-deploy kubernetes verify` 只接受 catalog 驱动的 qualification `verify` phase，MUST NOT 被描述为 install/backup/restore/upgrade/recovery 命令。所有路径都不得用启动 hook 隐式 migration 或取消任务；命令失败必须保留已完成阶段和可重试下一步。（来源：[Issue #93](https://github.com/Suknna/quoin/issues/93)、ADR-0001）
- **OPS-UPGRADE-005 —** 新版本接受新写入前 **MAY** 恢复升级前备份并回旧版本；接受新写入后 **MUST NOT** 只回滚镜像，回退 **MUST** 显式恢复升级前备份。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.10）
- **OPS-UPGRADE-006 —** Git **MUST** 只保存版本化声明式 seed scenario 与期望断言，**MUST NOT** 提交人工制作的 SQLite/PVC 二进制。首版只验 fresh install；之后每版 **MUST** 从上一正式 Release manifest 获取真实 digest，启动 N-1 并经公开 HTTP/Runtime 路径创建用户、连接、告警、Attempt、Artifact、知识和成功备份，再验证 N-1→N 的 Compose/Kubernetes YAML 协调升级、migration、恢复及接受新写入前回滚；生成数据 **MUST** 只作该次 CI 证据。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.43）

## 12. Compose 与 Kubernetes YAML 交付

- **OPS-COMPOSE-001 —** Compose 的六服务 MUST 使用直接、可读的配置；后端服务可使用 `restart: unless-stopped`，并只依赖各自重连与 Ready，MUST NOT 用隐式全栈重启传播。前端生产服务不得运行开发服务器。（来源：[Issue #93](https://github.com/Suknna/quoin/issues/93)）
- **OPS-K8S-001 —** 普通 Kubernetes YAML MUST 明确入口 Caddy、前端静态服务、Quoin、Plinth、Lintel、Stele 的职责、服务发现、持久卷、Secret 引用、健康检查和安全上下文；不得以 Helm 模板、values 或 Ingress Controller 作为前提。Caddy 必须按明确优先级转发 API、认证、SSE、noVNC WebSocket 与 Stele 入口，SPA fallback 不得吞掉这些请求。（来源：[Issue #93](https://github.com/Suknna/quoin/issues/93)）
- **OPS-K8S-002 —** 入口 Caddy MUST 终止 TLS 并在同一公共 Origin 下分流前端页面和 Quoin API；前端容器自身实际提供静态文件，不使用共享资源卷让 Caddy 托管。静态页面安全头由实际响应层承担，HSTS 继续仅由 TLS 终止层拥有。（来源：[Issue #93](https://github.com/Suknna/quoin/issues/93)、SEC-HEADER-001/002）

## 13. 验证门与证据边界

- **OPS-VERIFY-001 —** CI **MUST** 在一次性真实 Docker Compose 环境和真实 Kubernetes 测试集群（kind 或等价）分别完成安装与运行验收，**MUST NOT** 用 template/lint/build 代替实际启动和行为验证。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.33）
- **OPS-VERIFY-002 —** 原生 amd64 与原生 arm64 的最小矩阵 **MUST** 各自覆盖：五个应用镜像（Quoin、Plinth、Lintel、Stele、前端）按多平台 index digest 启动；探针与 metrics scrape；首次自动秘密引导及既有数据缺秘密 fail-closed；秘密→Admin→长期 workload 启动门（含 Admin Job 失败/重试且长期 workload 从未提前启动）；首次 Admin 登录；Plinth/Lintel 通过 attached stdin 一次性注册并在替换后拒绝旧长期 token；Plinth Bash/固定工具目录与 Landlock/seccomp 对抗自检；Lintel 真浏览器/noVNC/身份卷/trace；Stele Delivery；含 Artifact 的成功备份、helper 不持有 Web 凭据的 Admin UI 触发 + ops 指标观测路径与不可达时离线 fallback；停机恢复；post-restore verify 把 maintenance + 全 Runtime revoked + 连接待重校验识别为唯一预期隔离而不是普通失败；恢复后的 Session/Runtime/告警凭据失效；从上一 Release 动态造数后的升级与接受新写入前回滚；复用既有卷的服务重建；SIGTERM；存储故障；sentinel 泄漏扫描。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.33、Q17.34、Q17.43）
- **OPS-VERIFY-003 —** 发布门 **MUST** 实际验证离线归档签名、解包、registry 导入和 digest 读回。`quoin-deploy ... verify` **MUST** 校验 Release manifest 与 Sigstore subject、实际 workload image digest/版本、配置 Schema、固定副本/端口/安全上下文/卷、`/livez`/`/readyz`/`/metrics`、Runtime 注册/版本与存储探测；Kubernetes 路径在需要集群内访问时 **MUST** 创建同 Release verifier Job，Compose 路径 **MUST** 创建同 network 一次性 verifier service，均不得持有产品用户或外部连接凭据。输出必须是可保存的结构化检查清单，失败项带稳定 code 和恢复动作。普通 Kubernetes YAML 解析/应用、Compose config、OpenAPI/SQL/Proto/JSON Schema 校验 **MUST** 继续作为低层门禁，但其成功 **MUST NOT** 被报告为真实安装、恢复、升级或双架构运行通过。（来源：[Issue #17](https://github.com/Suknna/quoin/issues/17) Q17.10/Q17.33/Q17.39）
- **OPS-VERIFY-004 —** 机器契约一致性 fixture **MUST** 至少证明：普通 Kubernetes YAML 与 Compose 的必需服务、Secret/卷引用和安全边界可解析且一致；历史 Chart/生成配置证明不得被当作新架构通过证据；metrics 的 OpenAPI/SQL/Proto 外部枚举与目录引用集合严格相等且目录自有值带 authority；Plinth 镜像内 Debian package/path/version 等于工具目录；基础镜像、Playwright tag 源码、按平台派生的 Chromium URL 与实际 digest/hash 等于 release input lock；Backup Run 状态机拒绝非法跃迁、双 active、重复 scheduled boundary、在线/离线 actor 组合、终态改写与 DELETE；Release manifest 接受带 registry hostname/port 的 repository、拒绝缺失镜像/helper 平台或资产哈希、接受 SemVer prerelease/build asset 名并包含结构化验收摘要；`readiness-response.schema.json` 拒绝未知 reason 与字段关系冲突；每个外部 Sigstore bundle 的 subject 等于 manifest 中对应对象 digest 或实际 blob SHA-256。（来源：[SPEC-AUTHORITY-003](README.md#权威源与事实所有权)、[Issue #17](https://github.com/Suknna/quoin/issues/17)）

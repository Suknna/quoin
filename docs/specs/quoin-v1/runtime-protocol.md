# Quoin v1 Runtime 协议

**状态：Draft**

> **浏览器运行时已移除（2026-09）：** Lintel 浏览器运行时（`RUNTIME_SLOT_LINTEL`、Browser Operation、跨 Runtime 子执行、BrowserTunnel/noVNC、Journey Catalog、trace/screenshot Artifact kind）已从 proto 与实现中彻底删除，对应字段编号 reserved；历史冻结 attempt 与旧库中的浏览器数据不再保证可解析。文中浏览器会话语义仅作历史解读。

**Non-normative：** 本文件（CATEGORY=`RUNTIME`）承载 Quoin、Plinth、Stele 组件之间的 gRPC 协议语义：组件 mTLS 身份、Proto 契约指纹握手、控制流、任务派发与调和、lease/fencing、Plinth 模型/工具调用、Artifact 上传与按需读取、连接凭据 grant 与告警接入。机器可表达的 service、RPC、message、stream 与 wire-level 枚举由 [`contracts/runtime.proto`](contracts/runtime.proto)（package `quoin.runtime.v1`，SPEC-VERSION-002）唯一拥有（SPEC-AUTHORITY-001/002）；本文件只通过相对路径与稳定符号引用它，不复制字段清单。持久化权威为 `persistence.md` 与 `contracts/sql/schema.sql`；前端→Quoin 的 HTTP 面（含 reveal 流程）为 `http-api.md` 与 `contracts/openapi.yaml`（HTTP-SCOPE-003）。

> **现状与迁移：** #97 已同步替换冲突的指标执行输入：版本化业务声明的显式指标接入引用决定 grant，`resource_refresh_run` 已移除。2026-09 引擎退役后 `config_verification_run` scope、其执行/结果 schema 与 `ScopeType` 枚举值 5/9 一并删除（proto 按编号 reserved）；所有切片继续保留非秘密 grant、冻结版本、取消和审计边界。

## 1. 范围与权威

- **RUNTIME-SCOPE-001 —** 组件 gRPC 的 service、RPC、message、stream 方向与枚举值 **MUST** 只由 `contracts/runtime.proto`（`quoin.runtime.v1`）定义；本文件 **MUST NOT** 声明 proto 中不存在的服务、消息、字段或枚举值（SPEC-AUTHORITY-001/003）。
- **RUNTIME-SCOPE-002 —** 本文件 **MUST** 只拥有无法由 proto 表达的跨流语义：握手顺序、身份裁决、lease/fencing、调和、提交顺序裁决、故障与恢复；不重复 proto 已表达的形状。（来源：README「权威源与事实所有权」、Issue #8）
- **RUNTIME-SCOPE-003 —** locator（attempt、operation、artifact、source、credential 等）在 proto 中 **MUST** 使用 `int64`，与 SQLite INTEGER 及 HTTP 十进制字符串表示一致（DATA-IDENT-002）；`0` 表示无该 locator，边界校验见 RUNTIME-VALIDATION-004。
- **RUNTIME-SCOPE-004 —** 数值型协议调优参数（heartbeat 周期、lease 时长、上传 chunk 大小、流队列深度、重附着宽限期、轮换窗口）**MUST** 由原型测量后作为各应用构建输入的内部常量冻结并由相关组件共享，**MUST NOT** 成为 Kubernetes YAML、Compose 输入、Admin 设置或组件自由组合配置；本文件与 proto 只拥有字段类型与语义（Timestamp/Duration/uint64/uint32），具体数值由版本化构建源锁拥有。（来源：CONTEXT「执行尝试」「健康语义」、Issue #11 研究结论、Issue #17 Q17.1/Q17.22）

## 2. 身份与认证

- **RUNTIME-AUTH-001 —** Plinth **MUST** 主动出站拨号 Quoin gRPC server（维持只出站部署，Q2 冻结）；TLS **MUST** 只承担服务端身份与传输保护，**MUST NOT** 建立 mTLS 客户端身份。（来源：CONTEXT「服务身份」、架构记忆 #5860）
- **RUNTIME-AUTH-002 —（ADR-0009 重写）** 内部组件身份 **MUST** 由部署 CA 签发的 mTLS 客户端证书建立：TLS 握手验证双方，组件身份取自已验证链叶证书 CN（plinth/stele）。不存在注册、一次性令牌、长期 Bearer 或其下发路径；证书由部署密钥 bootstrap 签发、经部署 Secret 挂载，**MUST NOT** 进入任何消息体、日志或数据库。
- **RUNTIME-AUTH-003 —（ADR-0009 重写）** 服务授权按 CN 硬映射：`RuntimeControl`/`ArtifactService` 仅接受 CN=plinth，`SteleRelay` 仅接受 CN=stele；客户端证书 **MUST** 携带 ClientAuth EKU 且由部署 CA 签名（监听器 `RequireAndVerifyClientCert` 强制）。Attempt 派发绑定当前活动控制流（boot/epoch），不再存在 slot 注册状态或凭据指针。
- **RUNTIME-AUTH-004 —** 认证失败（令牌无效、slot 吊销、Proto 契约指纹缺失/无效/不匹配、epoch 回退）**MUST** 在握手阶段以 `HelloAck{accepted=false, reject_reason}` 拒绝并关闭流；组件 **MUST NOT** 进入 Ready。（来源：CONTEXT「服务身份」「健康语义」）
- **RUNTIME-AUTH-005 —** 连接凭据与模型供应商凭据 **MUST** 只由 supervisor 持有并注入类型化工具；Plinth worker **MUST NOT** 读取状态卷、环境变量或任何凭据文件；`FetchCredentialGrant` 是 supervisor-only RPC（RUNTIME-GRANT-002），worker 进程不得持有该调用能力（CONTEXT「模型调用边界」、架构记忆 #5868）。
- **RUNTIME-AUTH-006 —（ADR-0009 收窄）** 注册制 token 家族（一次性注册令牌、长期 Bearer、IssueToken 轮换消息）已整体退役；`alert_source_credentials.digest` 仍是告警源接入 bearer 的 SHA-256（32 字节原始二进制）。内容 digest（`AttemptInputSnapshot.content_digest`/`ResultPayload.content_digest`/`ArtifactUploadHeader.sha256`）是原始 32 字节二进制，用 `bytes` 承载，**MUST NOT** 做文本编码。（来源：CONTEXT「服务身份」、Issue #11 第一轮审阅、ADR-0009）

## 3. 连接与握手（`RuntimeControl.Connect`）

- **RUNTIME-CTRL-001 —** 每个 slot **MUST** 至多一条活动控制流；Quoin 在内存临界区维护连接投影，新连接（`connection_epoch` 更大）**MUST** 替换旧连接并关闭旧流，旧流上未完成的领域动作 **MUST NOT** 产生权威状态（RUNTIME-CTRL-009、RUNTIME-TASK-005/008）。控制流与 Artifact 流是不同 RPC；v1 **MAY** 共用同一 TCP/HTTP-2 channel，**MUST NOT** 强制独立 channel；若原型证明互相干扰，部署配置再拆分。（来源：CONTEXT「服务身份」、Issue #11 任务约束）
- **RUNTIME-CTRL-002 —** 连接首帧 **MUST** 为 `Hello`（slot、boot_id、connection_epoch、统一 Proto 契约指纹）；Quoin **MUST** 先完成认证与握手校验再回 `HelloAck`；握手完成前任何其他消息 **MUST** 被忽略或拒绝。
- **RUNTIME-CTRL-003 —** 统一 Proto 契约指纹 MUST 与 Quoin 按固定排序、无歧义编码计算的完整权威 protobuf 文件集合指纹严格相等（`==`）；缺失、无效或不匹配时 MUST 以明确的契约不匹配拒绝并使组件不 Ready。发布版本不同本身不得拒绝连接；不提供协商、降级或跨契约混跑（RUNTIME-VERSION-001）。
- **RUNTIME-CTRL-004 —** `boot_id` **MUST** 在每次进程启动时重新生成；`connection_epoch` 是 boot-local 计数器，**MUST** 在该 boot 的每次连接时递增（首条 >= 1）。Quoin 只在同一 `(slot, boot_id)` 内拒绝非单调（<= 该 boot 上次接受值）的连接（`EPOCH_STALE`）；新 boot 的首个 epoch 可重新从 1 开始，接受新 boot 后旧 boot 的全部流按 RUNTIME-CTRL-009 失效。（来源：Issue #11、RUNTIME-CTRL-009）
- **RUNTIME-CTRL-005 —** `Heartbeat` **MUST NOT** 改写任何持久状态：只更新内存瞬时投影，不写任何持久状态；通用 Attempt `Capacity` 只作提示。（来源：CONTEXT「健康语义」、Issue #14）
- **RUNTIME-CTRL-006 —** 每条流的每一端 **MUST** 使用单一 send loop / recv loop；发往对端的消息 **MUST** 进入有界队列，队列溢出 **MUST** 可观察（部署内部指标）且 **MUST NOT** 静默丢弃领域消息（派发、取消、结果）。
- **RUNTIME-CTRL-007 —** `GoAway` 是 Quoin 结束连接的尽力而为通知；实际关闭以 RPC 结束为准，客户端 **MUST NOT** 依赖 `GoAway` 送达；`SHUTTING_DOWN` 表示可重试的暂时不可用，`REVOKED`/`ROTATED`/`REPLACED` 表示必须按 RUNTIME-REVOKE-001 处理。
- **RUNTIME-CTRL-008 —** 物理消息重复投递 **MUST** 是幂等的：领域事实按 `attempt_id`+`boot_id`+`connection_epoch` 去重；对端不重复提交。
- **RUNTIME-CTRL-009 —** 每个 `ControlEnvelope` **MUST** 携带四个 envelope 字段（proto 强制形状，本条款定义语义）：`message_id`（当前连接内按方向单调递增且唯一，用于对 gRPC 缓冲重放/透明重试的物理去重：同 `(slot, boot, epoch, direction, message_id)` 的重复投递 **MUST** 被忽略、不重复执行）、`connection_epoch` 与 `boot_id`（除 `Hello` 外 **MUST** 等于 Quoin 当前已接受流上下文；不一致 **MUST** 丢弃且最多审计，**MUST NOT** 产生任何状态变化）、`correlation_id`（请求-响应对关联：`Hello`↔`HelloAck`、`DispatchAttempt`↔`AttemptAccept/AttemptReject`、`ReconcileRequest`↔`ReconcileReport`、`ResultProposal`↔`ResultAck`、`CancelAttempt`↔`CancelAck`、`IssueToken`↔`TokenPersisted`、`BeginModelCall`↔`BeginModelCallAck`、`CompleteModelCall`↔`CompleteModelCallAck`、`BeginToolCall`↔`BeginToolCallAck`、`CompleteToolCall`↔`CompleteToolCallAck`、`ToolResultDelivery`↔`ToolResultDeliveryAck`（回带原子执行请求关联）；0 = 无）。**所有**会写权威状态的消息（`AttemptAccept`/`AttemptReject`/`ResultProposal`/`CancelAck`/`TokenPersisted`/`ReconcileReport`/`BeginModelCall`/`CompleteModelCall`/`BeginToolCall`/`CompleteToolCall` 等）在事务提交前 **MUST** 复核当前活动流上下文（slot+boot+epoch）与 envelope 一致；旧流迟到消息（新 epoch 已接受后到达的旧流 buffered 消息）一律按上文丢弃/审计，旧流上未完成的领域动作 **MUST NOT** 产生权威状态（RUNTIME-CTRL-001）。`Hello` 的 envelope 字段描述提议的连接身份（epoch 为提议值，可不同于当前活动流）。（来源：Issue #4 研究证据、Issue #11 第一轮审阅）
- **RUNTIME-CTRL-011 —** Config Verification 的 PromQL check 与 discovery、以及定时巡检的机械采集 **MUST** 共用同一派发、结果、取消和调和路径（RUNTIME-TASK-001..012、RUNTIME-CANCEL-001..003）；各 Run 状态由 SQL 机器权威推进。Config Verification 的 `Passed` **MUST** 只在全部 check 形成 ok+Evidence 且所有 discovery 子 Attempt 已收口后落库；discovery 结果只保留为 Config Verification 证据，不产生正式资源投影。结果与取消按 SQLite 提交顺序裁决（DATA-TX-005）。（来源：[CONTEXT「业务系统配置版本」](../../../CONTEXT.md#业务系统配置版本)、[CONTEXT「观测资源」](../../../CONTEXT.md#观测资源)、[#97](https://github.com/Suknna/quoin/issues/97)）

## 4. 任务派发与调和

- **RUNTIME-TASK-001 —** Quoin **MUST** 先持久化 `execution_attempts`（`attempt_id` 权威）再派发：派发事务在同一事务内设置 `runtime_slot`/`boot_id`/`connection_epoch`/`lease_until`（`Assigned`）并复查目标 slot `registered` 且 current 指向已确认未退休凭据（DATA-ATTEMPT-001、DATA-RUNTIME-001）；事务提交后 **MUST** 才发送 `DispatchAttempt`。
- **RUNTIME-TASK-002 —** `DispatchAttempt` **MUST** 携带 attempt_id、attempt_type、scope_type、scope_id、可选 check_key、Config Verification 的 check 子 Attempt 必填 `plan_key`、其 discovery 子 Attempt 必填 `discovery_key`、`lease_deadline`（有限 lease）、完整 `AttemptInputSnapshot`（RUNTIME-TASK-011）与可选的 `requested_by_tool_call_id`；lease 时长数值为部署配置（RUNTIME-SCOPE-004）。
- **RUNTIME-TASK-003 —** Attempt 类型与 slot 的固定映射 **MUST** 与 schema CHECK 一致：`scope_type=run_check|observation_run` 的 `inspection_collection` 按冻结输入固定映射：PromQL check 与来源观测 discovery 只派发 `plinth` supervisor（DATA-INSPECT-003）；`initial_analysis`/`investigation`/`inspection_analysis`/`knowledge_extraction`/`embedding`/`connection_probe` 只派发 `plinth`（DATA-RUNTIME-001b、DATA-ATTEMPT-001）。（来源：[Issue #13](https://github.com/Suknna/quoin/issues/13)、[#97](https://github.com/Suknna/quoin/issues/97)、DATA-ATTEMPT-001）
- **RUNTIME-TASK-004 —** Runtime **MUST** 对每个 `DispatchAttempt` 回 `AttemptAccept` 或 `AttemptReject`：Accept 后 Quoin 写 `accepted_at` 并转 `Running`；`NO_CAPACITY` 拒绝时 Attempt **MUST** 保持 `Assigned`（绑定不可改），Quoin **MAY** 幂等重发同一 `DispatchAttempt`（同 attempt_id/boot/epoch），超过部署内部重试策略后按 RUNTIME-TASK-009 终止；`INPUT_UNSUPPORTED`/`INTERNAL` 拒绝时 Quoin **MUST** 转 `Failed`（`provider_unavailable`）。
- **RUNTIME-TASK-005 —** lease 内同 boot 重连（`Hello` 的 boot_id 相同且 epoch 更大、lease 未到期）**MUST NOT** 重派：Quoin **MUST** 发送 `ReconcileRequest`（该 slot 当前 active 集合），Runtime **MUST** 回 `ReconcileReport`（实际运行集合），双方按 attempt_id 对齐。`Assigned` 未接受的 Attempt **MAY** 在调和后幂等重发。
- **RUNTIME-TASK-006 —** 对 `Assigned|Running` Attempt，新 boot（boot_id 不同）**MUST** 使旧 boot 绑定 Attempt 转 `Interrupted`（`lease_expired`）；slot 替换转 `Interrupted`（`replaced`），凭据吊销转 `Interrupted`（`revoked`），lease 到期无续期转 `Interrupted`（`lease_expired`）。已经提交 cancellation fence、状态为 `Cancelling` 的 Attempt 是例外：上述任一失联条件都必须按 RUNTIME-CANCEL-003 收敛为 `Cancelled`，不得改写为 `Interrupted`。（来源：CONTEXT「执行尝试」、DATA-ATTEMPT-001）
- **RUNTIME-TASK-007 —** `lease_until` **MAY** 由心跳或活动消息续期（每次 UPDATE 恰好递增 `row_version`，DATA-ATTEMPT-006）；续期判定数值为部署配置。
- **RUNTIME-TASK-008 —** 结果 **MUST** 经 `ResultProposal` 提交（attempt_id + boot_id + connection_epoch + outcome + 可选 termination_reason + `ResultPayload`）；Quoin **MUST** 按 attempt_id+boot+epoch 幂等裁决：旧 epoch、lease 已到期或 cancellation fence 已提交的迟到结果 **MUST NOT** 产生有效领域输出，只留审计（DATA-ATTEMPT-004）；`ResultAck{accepted}` 回传裁决。（来源：Issue #13、DATA-ATTEMPT-004）
- **RUNTIME-TASK-009 —** 部分 token 后失败 **MUST NOT** 成为有效输出：Attempt `Failed` + 结构化 `TerminationReason`（与 schema CHECK 枚举一致）；成功前所有引用 Artifact **MUST** 经 `ArtifactService.Upload` 上传校验提交（DATA-ATTEMPT-005、DATA-ARTIFACT-006）。
- **RUNTIME-TASK-010 —** `AttemptProgress` **MUST NOT** 成为权威状态来源：显示性进度；权威进度由 `tool_calls`/`evidence` 持久记录承担（DATA-EVIDENCE-001）。
- **RUNTIME-TASK-011 —** 任务执行输入 **MUST** 由 Quoin 根据 `attempt_input_snapshots`/`attempt_input_items` 权威引用重建，并在派发时由 `AttemptInputSnapshot` 完整承载（**MUST NOT** 只传 digest 让对端自行重建）：`schema_kind` 为按 AttemptType、collection scope 与冻结 check/discovery kind 封闭映射的登记值，`canonical_json` 非空且 digest 匹配，Artifact/grant 只引用已冻结非秘密事实。`scope_type=run_check` 的输入按 check kind 封闭：PromQL check 的 `inspection_promql_execution_v1` canonical JSON **MUST** 通过 [inspection-promql-execution.schema.json](contracts/schemas/inspection-promql-execution.schema.json)，精确冻结 Attempt、Inspection Run、check、`evidenceAt`、PromQL mode/expression/range/step 与唯一 `config_thanos_query` 非秘密 grant locator；range 的 end 固定为 `evidenceAt`，start 由冻结 rangeSeconds 导出，Runtime 不得使用自己的时钟重算。`scope_type=observation_run` 的输入按对象封闭：`source_observation_execution_v1` 精确冻结 Attempt、Run、discovery key/selector/identity labels 与选定指标接入的唯一 `config_thanos_query` grant。对端拒绝未知 schema/digest/字段；秘密只经类型化 grant 下发。（来源：[Issue #13](https://github.com/Suknna/quoin/issues/13)、[#97](https://github.com/Suknna/quoin/issues/97)、DATA-ATTEMPT-003）
- **RUNTIME-TASK-012 —** `ResultProposal.payload` 的 `schema_kind` **MUST** 与 AttemptType 封闭匹配。`scope_type=run_check` 的 `inspection_collection` 按 check kind 封闭：PromQL check 只接受 `inspection_promql_result_v1` 并通过 [inspection-promql-execution.schema.json](contracts/schemas/inspection-promql-execution.schema.json)：success 必须带完整非 Artifact structured result、range 时精确执行窗口（start/end/step）与完整 Evidence proposal，error/gap 固定无 Evidence 并带封闭 gap code；Quoin 必须按冻结 input 重验返回 executionWindow。其它模型/分析类型继续使用登记的封闭 schema kind（config verification 的 `config_promql_result_v1`/`config_verification_discovery_result_v1` 已随引擎退役；未知 schema kind 的 inspection_collection ResultProposal 以显式 ResultAck 拒绝收口）。未知或不匹配 payload 以 `invalid_response` 失败且不得落库；不得使用未定义补通道或不透明日志。（来源：Issue #13、DATA-ATTEMPT-005）

## 5. 取消与结果裁决

- **RUNTIME-CANCEL-001 —** 用户取消 **MUST** 先由 Quoin 事务提交 cancellation fence（`Queued` 直接 `Cancelled`；`Assigned` 或 `Running` 先转 `Cancelling`）。`Assigned` 的 `DispatchAttempt` 可能已经在途，必须与 `Running` 一样发送 `CancelAttempt`；事务提交后 **MUST** 才发送 `CancelAttempt`（DATA-ATTEMPT-003、HTTP-COMMAND-005）。
- **RUNTIME-CANCEL-002 —** 成功结果与取消 **MUST** 按 SQLite 提交顺序裁决（DATA-TX-005）：成功先提交则取消返回已完成对象；取消先提交则迟到结果不产生有效消息/Report/Candidate，只留审计。
- **RUNTIME-CANCEL-003 —** Runtime 收到 `CancelAttempt` 停止后 **MUST** 回 `CancelAck`；Quoin 收到后转 `Cancelled`。同 boot transport detach 不是物理停止证明：fence 与其并发时 Attempt **MUST** 保持 `Cancelling`，并在同 boot reconnect 后重发 `CancelAttempt`；只有有效 `CancelAck`、新 boot 的实际运行集合调和或 lease/loss 才可收敛终态。旧流迟到的 `CancelAck`/`AttemptAccept` 按 RUNTIME-CTRL-009 envelope fence 丢弃。

## 6. Plinth 模型与工具循环

- **RUNTIME-AGENT-001 —** Plinth **MUST** 复用 Eino v0.9.13 的 ChatModel、OpenAI-compatible adapter、Message/Tool/stream/callback 基元，自行实现最小顺序 ReAct loop；**MUST NOT** 使用带默认总轮数上限的 ChatModelAgent/Runner 或供应商托管 AgenticModel。第一版不设置 Attempt 总模型轮数、总 Tool Call 数或总时长上限；单次 provider/外部 API 调用仍使用内部 deadline 与严格有界重试。（来源：Issue #13 Q13.1 A）
- **RUNTIME-AGENT-002 —** 每个物理 provider 请求前，Plinth **MUST** 先发送 `BeginModelCall`。Quoin 事务复核 Running Attempt、固定 agent/model capability、同一 `call_seq/retry_seq` 未存在、输入项与 digest 闭合后，创建 `model_calls(status=running)` 并绑定派发前已经冻结的模型 grant，提交后才回 `BeginModelCallAck{accepted=true}`。Plinth 只有收到 accepted Ack 并通过 supervisor-only `FetchCredentialGrant` 取得该 grant 后才能调用 provider；worker 永不看到 grant/connection/credential。（来源：DATA-TX-017）
- **RUNTIME-AGENT-003 —** `BeginModelCall.input_items` **MUST** 精确表达本次按序模型输入的权威来源与 digest，`rendered_request_digest` 必须是 supervisor 对 worker 实际请求规范化后的 SHA-256；Quoin **MUST** 复算来源闭合并持久化该实际请求 digest，使 renderer/version/source 可独立重建核对。上下文超预算时只允许从最旧端淘汰完整对话回合，Tool Call/Result 与所属 assistant turn 共同保留或共同淘汰，并记录 `evicted_turn_count`；**MUST NOT** 生成或复用摘要、rolling memory、replacement history。固定 System/当前用户消息/必要协议组自身超限时 Attempt 失败为 `CONTEXT_TOO_LARGE`。（来源：Issue #13 用户定案）
- **RUNTIME-AGENT-004 —** Chat streaming 的可见文本可经 `ModelTokenDelta` 转发 HTTP SSE，但 delta 是瞬时 UI 投影，**MUST NOT** 直接创建 Investigation Message 或成功输出；旧 epoch、未知/终态 Model Call、非单调 `delta_seq` 或 cancellation fence 后的 delta 必须丢弃。隐藏 reasoning/thinking token **MUST NOT** 通过该消息、日志或 Artifact 暴露。（来源：CONTEXT「模型调用边界」）
- **RUNTIME-AGENT-005 —** provider 返回或失败后 Plinth **MUST** 发送 `CompleteModelCall`。Quoin 在一个事务中封存 usage/latency/request ID/termination，并置物理调用终态；Chat 的规范 response 必须是 object 且总含 `tool_calls` 数组（无工具时为空），完整成功响应或任何已暴露的部分响应必须写 `model_call_outputs`（部分响应 `complete=0`）。成功响应中的全部 `ProposedToolCall` **MUST** 按 provider 顺序一次性验证并创建 pending `tool_calls`，随后在 `CompleteModelCallAck` 返回持久 ID、固定 `ToolFailureMode` 与必要的非秘密 grant 引用。任一 Tool schema/参数/路由不合法时，同一事务必须把物理 Model Call 与 Attempt 封存为 `invalid_response` 失败且不创建任何 Tool Call；**MUST NOT** 留下 running Model Call、先执行或部分创建 Tool Call。相同 model_call_id 的 `CompleteModelCall` 重放必须按已封存 output digest/outcome/tool_call IDs 幂等返回原 Ack；内容不一致必须冲突拒绝。wire `ModelCallFailureReason` 与 SQL `model_calls.termination_reason` 逐一映射为 `TIMEOUT->timeout`、`RATE_LIMITED->rate_limited`、`TRANSPORT_ERROR->transport_error`、`PROVIDER_UNAVAILABLE->provider_unavailable`、`CONTEXT_OVERFLOW->context_overflow`、`INVALID_RESPONSE->invalid_response`、`CANCELLED->cancelled`、`ARTIFACT_COMMIT_FAILED->artifact_commit_failed`。Attempt cancellation fence/终态已提交不是 provider 失败：Quoin 必须以 `CompleteModelCallAck.accepted=false` 且 `reject_reason=ATTEMPT_TERMINAL` 拒绝，不创建新的物理行或改写既有终态；accepted Ack 的 `reject_reason` 必须为 `UNSPECIFIED`。（来源：DATA-TX-017）
- **RUNTIME-AGENT-006 —** provider 传输重试 **MUST** 是显式物理行：同一 `call_seq`、`retry_seq+1`，且前一物理行已明确 `failed`、没有 `model_call_outputs` 行，并且失败原因严格属于 `timeout|rate_limited|transport_error`；`transport_error` 只允许 adapter 能证明请求未到达 provider 或没有不确定副作用时使用。`provider_unavailable`、任何已暴露部分响应、取消 fence、Attempt 已终态、`invalid_response` 或 `artifact_commit_failed` 均不得在同一 Attempt 自动重试；`context_overflow` 只有在未收到任何响应且下一物理行增加 `evicted_turn_count` 时才可显式重试，固定必需项本身超限直接 `CONTEXT_TOO_LARGE`。provider SDK 内建隐式重试必须关闭。下一次 Agent 推理使用 `call_seq+1,retry_seq=0`，**MUST NOT** 与物理重试混淆。（来源：Issue #13、DATA-AUDIT-003）
- **RUNTIME-AGENT-007 —** Tool Calls **MUST** 严格按 `provider_index` 顺序执行。Plinth 在任何副作用前发送 `BeginToolCall`；Quoin 只在父 Model Call 已完整成功、Attempt Running、前序 Tool Call 已终态且 grant/Tool 定义闭合时将 pending 推进 running 并回 accepted。`ToolFailureMode` 来自发布的固定 Tool 定义：`RETURN_TO_MODEL` 把失败作为已提交 Tool Result 继续下一轮；`FAIL_ATTEMPT` 立即失败 Attempt。模型或 worker不得覆盖。（来源：Issue #13）
- **RUNTIME-AGENT-008 —** Tool 结束后 Plinth **MUST** 发送 `CompleteToolCall`。Quoin 在同一事务校验固定 result schema，提交 ToolCall 终态、确定性 Evidence、Artifact 引用与模型可见 `committed_payload` 后回 `CompleteToolCallAck`；`RETURN_TO_MODEL` 失败的 `committed_payload` 必须由 Quoin 根据 `error_code` 与经脱敏的 `error_detail` 确定性生成有界规范 JSON。Plinth 后续 Model Call 只能使用 Ack 返回的已提交结果。取消先提交、旧 epoch、正文已过期、未提交 Artifact 或引用不闭合时拒绝完成；取消前已提交的 Tool/Evidence/Artifact 历史保留。（来源：DATA-TX-018）
- **RUNTIME-AGENT-009 —** 模型输出只是提案：Quoin 只做类型/结构、引用闭合、digest、状态与 fence 校验，**MUST NOT** 以程序给模型结论设置 verdict/severity 下限或判断内容正确性。Agent 最终输出仍必须经 `ResultProposal` 原子落为固定工作模式的领域对象；部分 token、未闭合 Tool Call 或未提交引用不得成功。（来源：Issue #13 用户边界、DATA-ATTEMPT-010）
- **RUNTIME-AGENT-010 —** Embedding 与 `connection_probe` **MUST NOT** 创建 Agent worker 或 ReAct loop；Plinth supervisor 直接执行 `contracts/connection-probes.yaml` 中按 Connection type 冻结的 action set。Model Provider probe 仍使用 `BeginModelCall`/`CompleteModelCall` 建立真实 chat/embedding 调用审计；Thanos probe 只使用专用 grant 与类型化 adapter。成功事实只能在同一事务提交到 `connection_probe_results` 及其唯一 typed child，并以与 header outcome 一致的 Attempt 终态封存；缺 child 或 outcome/Attempt 终态不一致不得提交。Model Provider 启用还必须显式选择闭合到 current pair、root binding 与当前 action-set 的 passed result，旧 `model_provider_capabilities` 不保留。（来源：Issue #13、Issue #21 Q21.36）

## 7. Plinth supervisor / worker 本地协议

- **RUNTIME-WORKER-001 —** `contracts/quoin/plinth/worker/v1/agent_worker.proto` 是 supervisor/worker 唯一机器协议，`architecture.md` 的 `ARCH-WORKER-*`/`ARCH-AGENT-*` 是其人类语义权威；本文件只规定该本地协议与 Quoin Runtime 协议的跨边界裁决，不复制 framing、完整消息状态机或 sandbox profile。（来源：Issue #13、ARCH-WORKER-001、ARCH-AGENT-001）
- **RUNTIME-WORKER-002 —** worker 的 Model/Tool/结果消息都只是提议。supervisor 必须先取得对应 Quoin `Begin*` Ack 才可发起 provider/Tool 副作用，并且只有在 Quoin 已提交完成事实后才可把完成结果返回 worker；`WORKER_LOCAL` 也必须经本地协议的 `ExecuteToolCall -> ToolCallStarted` 门后才能执行。（来源：Issue #13、ARCH-TOOL-001/002）
- **RUNTIME-WORKER-003 —** 收到 `CancelAttempt` 后，supervisor 必须按 `architecture.md` 的取消顺序执行；worker 的本地停止确认、EOF、stderr 或进程信号都不覆盖 Quoin cancellation fence，也不得自行裁决 Attempt 终态。（来源：Issue #13、ARCH-RECOVERY-001、DATA-TX-005）
- **RUNTIME-WORKER-004 —** worker 启动前必须通过 `architecture.md` 的 v1 同 uid Landlock + seccomp profile 真实自检；不能建立声明边界时 readiness/Attempt 以 `sandbox_unavailable` 失败且不得静默退化。隔离自检完成前不得发送 `StartAttemptAck`，Quoin 不得把该 worker 视为可执行。（来源：Issue #13 Q13.4 A、ARCH-WORKER-007/008）

## 8. Artifact 上传与按需读取（`ArtifactService.Upload`）

- **RUNTIME-UPLOAD-001 —** 每个上传 **MUST** 使用独立 client-stream：首帧 **MUST** 为 `ArtifactUploadHeader`（upload_id、attempt_id、boot_id、connection_epoch、owner、kind、retention_kind、sensitive、size_bytes、sha256、media_type），随后 0..N 个 `ArtifactUploadChunk`（offset 连续），可显式 `ArtifactUploadEnd`；Quoin 在收到 `size_bytes` 字节或 `end` 帧后裁决。Runtime 上传 kind 封闭为 `attachment|tool_result|report_file`；`verification_bundle|verification_attachment` 只能由 Quoin/Deployment Helper 的本地耐久路径创建，不经过 ArtifactService。（来源：Issue #11、DATA-ARTIFACT-006）
- **RUNTIME-UPLOAD-002 —** v1 **MUST** 整单重传，**MUST NOT** 实现 offset 续传；`upload_id` 在重试生命周期内稳定：同 upload_id 同摘要重试 **MUST** 返回原 `artifact_id`，同 upload_id 不同摘要/owner **MUST** 冲突拒绝（DATA-ARTIFACT-006）。
- **RUNTIME-UPLOAD-003 —** Quoin 提交 **MUST** 依 DATA-ARTIFACT-001 的耐久顺序：临时文件写入并校验 hash/大小 → fsync 临时文件 → 按 SHA-256 原子 rename → fsync 最终父目录 → 才提交 SQLite 引用事务（`artifact_blobs` + `artifacts` + ledger `uploading->committed`）；引用事务失败 **MUST** 将文件作为孤儿清理。
- **RUNTIME-UPLOAD-004 —** `committed` 裁决 **MUST** 满足全部正向条件（DATA-ARTIFACT-006 与 SQL 触发器）：上传要求 Attempt `Running` 且 `boot_id`/`connection_epoch` 非空并与 upload 一致；JOIN 的 `artifacts`+`artifact_blobs` 与 ledger 的 kind/retention_kind/sensitive/owner_type/owner_id/sha256/size_bytes 精确匹配；任一条件不满足 **MUST** 置 `rejected` 并返回 `UploadRejectReason`（旧 Attempt 终态、替换后 ABA、boot/epoch 不符、元数据不符均不得 commit）。
- **RUNTIME-UPLOAD-005 —** ledger 来源字段与 `artifact_id`/`committed_at` 提交后 **MUST NOT** 改写；历史 **MUST NOT** 删除。
- **RUNTIME-UPLOAD-006 —** chunk 大小与流背压数值为部署配置（RUNTIME-SCOPE-004）；队列溢出 **MUST** 可观察且不静默丢弃。
- **RUNTIME-ARTIFACT-001 —** Tool 结果字节数 `> 50 * 1024` 或行数 `> 2000`（任一先满足）时 Plinth **MUST** 以有界流提交现有 `kind=tool_result,retention_kind=generated` Artifact；模型只收到可判别预览、Artifact locator、media type、大小、行数与 hash，并被告知可调用固定 Artifact Read/Grep Tool。文件/搜索结果预览优先头部，日志/命令输出优先尾部；上传失败不得把截断预览伪装成完整成功。（来源：Issue #13 用户定案；Pi/OpenCode 上游研究）
- **RUNTIME-ARTIFACT-002 —** `ReadText`/`GrepText` 是 supervisor-only、Attempt-scoped RPC：Quoin 必须校验 Runtime Bearer、slot=plinth、Attempt Running、boot/epoch 当前且 `attempt_artifact_grants` 已授权；Artifact 必须是允许的文本 media type 且 `body_expired=0`。worker 只经本地固定 Tool 请求，永不获得 Runtime Bearer、storage_key 或 Quoin PV 路径。（来源：Issue #13 用户定案、ARCH-INPUT-004、DATA-ARTIFACT-003）
- **RUNTIME-ARTIFACT-003 —** Read/Grep 的行数、匹配数、上下文行和响应字节数使用服务端固定上限；`start_line` 1-based，Grep 使用 RE2 语义以避免不受控回溯。响应必须回传完整 Artifact 的 size/hash/media type 与 eof/truncated，使模型能判断是否继续读取，**MUST NOT** 暗示已返回完整正文。（来源：Issue #13 用户定案、ARCH-INPUT-005、DATA-ARTIFACT-007）
- **RUNTIME-ARTIFACT-004 —** generated Artifact 到期由现有 GC 只清理正文；Artifact owner/hash/media type/大小/来源历史继续保留。正文已过期时 Read/Grep 返回 `FAILED_PRECONDITION`（detail=`ARTIFACT_BODY_EXPIRED`），若它是当前 Attempt 不可替代的必要输入则 Attempt 失败为同名结构化原因，**MUST NOT** 从非权威本地缓存继续。（来源：Issue #13 用户定案、ARCH-OUTPUT-004、DATA-ARTIFACT-003/004）

## 11. 连接凭据 grant（`RuntimeControl.FetchCredentialGrant`）

- **RUNTIME-GRANT-001 —** 接入凭据必须由 Quoin 以不可变 Attempt grant 授权。模型/Embedding grant 在派发前冻结；指标能力只在任务或具体 Tool Call 按显式授权接入引用确定性路由后创建，绝不回退到全局或第一个接入。#97 中 PromQL 检查使用 `config_thanos_query` grant；来源观测 discovery 创建 `source_observation_execution_v1` 输入的 `inspection_collection` Attempt，并同样冻结所选指标接入 grant。`resource_refresh_run`/`config_verification_run` 不再是有效 scope 或 grant 来源。模型、用户、worker 和 Runtime 均不得选择凭据，秘密正文 **MUST NOT** 进入 worker、Dispatch、模型上下文、日志或审计。（来源：[CONTEXT「接入」](../../../CONTEXT.md#接入)、[CONTEXT「观测资源」](../../../CONTEXT.md#观测资源)、[#97](https://github.com/Suknna/quoin/issues/97)、ADR-0002）
- **RUNTIME-GRANT-002 —** supervisor **MUST** 经 `FetchCredentialGrant` 获取秘密：Quoin 校验 grant/Attempt/boot/epoch/slot，并重验 Connection current generation 的 root binding revision，随后在受控内存中以 SEC-KEY-003 的 AAD 解密。成功只返回类型化非秘密 config 与 secret 给 supervisor，worker 不得调用。binding 不匹配或 AEAD 认证失败必须拒绝 grant、隔离 Connection 并写无秘密审计，绝不尝试旧 key/旧 generation/空凭据。（来源：DATA-CONN-002/009、Issue #16、SEC-KEY-005）
- **RUNTIME-GRANT-003 —** grant 生命周期 **MUST** 只存在于 Attempt 运行期间：派发或具体 Tool 授权时创建、Attempt 达到终态（Succeeded/Failed/Cancelled/Interrupted）时 Quoin **MUST** 撤销获取资格并释放内存秘密，持久 grant 行继续作为不可变审计历史；Attempt 未 `Running` 或 grant 已撤销时 `FetchCredentialGrant` **MUST** 返回 `FAILED_PRECONDITION`（或 `NOT_FOUND`，detail 说明）；supervisor 侧 **MUST** 在 Attempt 终态后丢弃内存秘密，**MUST NOT** 落盘、进入日志/审计或响应快照。成功响应经 TLS 每次可重取（Attempt Running 期间幂等），但 supervisor **MUST NOT** 持久化。（来源：Issue #13、DATA-CONN-008）

## 12. Stele 告警接入（`SteleRelay`）

- **RUNTIME-STELE-001 —（ADR-0009 重写）** Stele 以部署 CA 签发的客户端证书（CN=stele）经 mTLS 认证 `SteleRelay` 两个 unary RPC；无注册、无 slot、无 service token。
- **RUNTIME-STELE-002 —** Stele **MUST** 经 `GetCredentialSnapshot` 获取版本化只读凭据 digest 快照并仅内存缓存；快照只包含 SQL 中 `Active|PendingRetirement` 的可认证 generation，Retired 必须消失。未成功加载快照拒绝接收 Delivery；快照版本单调递增，Stele 提交时回传（DATA-ALERT-008）。
- **RUNTIME-STELE-003 —** `Deliver` **MUST** 携带 `relay_id`（每次外部请求生成，内部重试复用）、`source_id`、`credential_id`、`credential_snapshot_version`（>= 1）、`protocol`、精确原始 `body` 与 `received_at`；Quoin **MUST** 在 Delivery 事务内重验来源启用、凭据有效性与归属，relay_id 幂等（DATA-ALERT-001/008）。
- **RUNTIME-STELE-004 —** Delivery 使用新 generation 首次成功提交时，同一 SQLite 事务写该 generation `first_used_at` 并把其 supersedes 指向的旧 generation转为 PendingRetirement；Stele 后续快照继续包含新旧两个 generation，直到 Admin 显式退休旧值。系统不得以墙钟或首次成功自动移除旧 digest。（来源：Issue #16、SEC-SERVICE-002、DATA-ALERT-009）
- **RUNTIME-STELE-005 —** `DeliveryRelayResponse` 状态 **MUST** 映射 HTTP 语义：`ACCEPTED`=204（单事务保存 Delivery、处理结果并更新全部正常 Occurrence 后才返回）；`REJECTED`=4xx（永久拒绝，Alertmanager 不重试）；`UNAVAILABLE`=5xx（可重试）。提交失败或结果不确定 **MUST NOT** 返回 ACCEPTED（CONTEXT「Stele」）。
- **RUNTIME-STELE-006 —** 每个 unary 请求 MUST 携带统一 Proto 契约指纹，并与 Quoin 严格相等（RUNTIME-VERSION-001）；缺失、无效或不匹配 MUST 返回 `FAILED_PRECONDITION` 且 MUST NOT 处理请求（Stele 不 Ready、拒绝接收 Delivery）。凭据快照必须提供同一非秘密指纹供 Stele 核对；发布版本仅用于展示与溯源，不参与准入。

## 13. Proto 契约与兼容

- **RUNTIME-VERSION-001 —** Quoin、Plinth 与 Stele 的 Connect、Register、重连和 Stele unary 准入 MUST 使用同一 Proto 权威契约的确定性 SHA-256 指纹。权威集合仅为 `contracts/runtime.proto` 与 `contracts/quoin/plinth/worker/v1/agent_worker.proto`；按固定路径排序与无歧义内容编码计算。任一权威文件的任何内容变化（包括兼容字段增加）都必须改变指纹并要求全部应用重新构建。发布版本可不同且仅作展示、审计和溯源；认证、凭据轮换/吊销、TLS、slot、epoch 与其他既有安全前提继续独立校验。（来源：[Issue #93](https://github.com/Suknna/quoin/issues/93)、ADR-0001）
- **RUNTIME-VERSION-002 —** proto 字段编号一经分配 **MUST** 永不复用；删除字段 **MUST** 使用 `reserved` 声明并保留编号；oneof 成员与普通字段共享编号空间（SPEC-VERSION-003）。
- **RUNTIME-VERSION-003 —** 指纹的计算输入必须只来自 RUNTIME-VERSION-001 所列权威源；生成代码、单一 proto package 版本、运行配置和发布版本均不得替代或伪造该身份。缺失、无效或不匹配必须 fail closed，且不得协议协商、降级或声称跨契约滚动升级无中断。

### RUNTIME-TASK-013 — Inspection Report ResultProposal

当同一 `Inspection Run` 的 collection 已收口（`Completed|CompletedWithGaps`）后，Quoin 可创建一个 `inspection_analysis` / `scope_type=run` Plinth Attempt。其唯一输入为 `inspection_analysis_v1`：Run/config-version/plan 身份、Quoin 预分配并以结构化事实（`attempt_input_snapshots.inspection_report_version`）冻结的 `reportVersion`、恰好一个匹配该 Run 的 locator item、已冻结的有序 Evidence/Artifact/Knowledge locator（必须覆盖该 Run 的每个 check result）与模型合同。模型读取 Evidence 内容的路径是 Quoin 为每份 run Evidence 物化的不可变 content-addressed Artifact（`artifacts.owner_type='evidence'`），经 `attempt_artifact_grants` 冻结为输入并由 Report closure 校验归属。Plinth 成功必须提交 `inspection_report_result_v1`（含精确 `modelCallId`）；Quoin 重新验证 Attempt/Run、输入引用闭包、canonical digest 后在一个 SQLite 事务内写入下一个版本的 immutable Report、全部有序引用和 Attempt 成功：`evidenceDigest` 必须等于 `sha256(evidenceIds 的 canonical JSON)`，`resultDigest` 必须等于对 `inspection_report_result_v1|attemptId|inspectionRunId|modelCallId|success|content|三组 locator JSON|evidenceDigest|promptDigest` 的 sha256。相同 digest 的重投递幂等；不同 payload、旧 boot/epoch、取消或租约后结果拒绝。失败结果不创建 Report 或虚构 Evidence；`modelId` 与 `promptDigest` 只能来自同一条 succeeded model call。

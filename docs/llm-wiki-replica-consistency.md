# 常驻 /wiki 副本一致性：文档版本与事务变更日志

- 状态：设计稿，未实施；2026-09-30。
- 对应 [Issue #111](https://github.com/Suknna/quoin/issues/111) 的后端/Runtime 协议；前端由用户指定的另一个模型按后端冻结契约接入。
- 对应[总体设计](llm-wiki-design.md)。按用户新约束，将前稿 Git ref/checkout 协议替换为现有 SQLite 文档存储与变化游标。
- 参考：[存储选型](research/wiki-storage-alternatives-20260930.md)、[Kubernetes 与文件同步边界](research/resident-wiki-sync-20260930.md)。

## 1. 保持的约束

Quoin 是唯一持久权威；Plinth 一个 Pod 生命周期内保留一份 `/wiki/`，不每任务复制或同步；模型使用 read/write/bash/grep。读任务可并行，Wiki 编辑与目录刷新独占。编辑产生的草稿保存 Quoin 后才确认，正式发布不经过人工审批。

**选择的协议：Snapshot + transactional changes feed + per-document expected revision + draft receipt。** 这是一个权威到文件投影的复制机制，不是多主数据库复制。

## 2. 存储位置与游标

```text
Quoin 持久库：
  文档/不可变 revision、草稿、change sets/items、审计与命令结果

Plinth Pod emptyDir：
  /wiki/                  跨任务共享的 Markdown/报告文件
  supervisor 私有状态    appliedSeq、manifest、草稿确认与编辑身份
```

| 标识 | 作用 |
|---|---|
| wikiId + syncEpoch | 绑定权威知识域与同步历史，恢复旧备份后更换 epoch，避免游标 ABA |
| publishedSeq | Quoin 已提交的正式变更批次序号 |
| appliedSeq | 本副本已完整应用并校验的最后批次 |
| projectionId | 副本内容范围/规则版本，变化时重新引导，不能沿用旧游标假装完整 |
| docId + revisionId + path/hash | 文件稳定身份、正文版本与路径，用于比对、改名及引用 |
| editId + draftSequence | 当前编辑及最新已确认草稿的幂等身份 |
| bootId + connectionEpoch | 复用运行身份围栏，拒绝旧 Pod 或过期任务写入 |

正文只在不可变修订中保存；feed、命令账本和 task 记录仅引用它。Plinth 不持有可独立发布正式版本的数据库。

## 3. 下行：同步只跟随正式版本变化

### 3.1 初始快照

1. Pod 首次启动向 Quoin 请求允许的 Wiki 投影。
2. Quoin 在一致性读事务中冻结序号 S 和文档 manifest；各项绑定不可变 revisionId。
3. 将这些版本的内容传给 Plinth，校验路径、大小、hash、删除/权限状态。
4. 完整物化后设 appliedSeq=S，开放 Wiki 就绪。
5. 随后拉取 seq>S 的变化，补齐快照传输期间的新提交。

不在长时间传输中重读 current 指针，避免混合多版；不可变修订需在传输期间保留。快照不完整不能开一个空目录让模型以为没有知识。

### 3.2 正常增量

- Quoin 正式发布的事务同时写 ChangeSet/ChangeItems；通知在提交后发出。
- Plinth 收到通知只得知有新序号，按 appliedSeq 拉取变化。低频轮询作丢通知的兜底，建议起点 30 秒。
- 变化包含新增/修改/删除/改名/恢复及目标 revisionId，不每次搬全部 Markdown。
- 一个批次的所有文件在本地独占状态下应用；全部校验后才更新 appliedSeq。
- 有读任务、编辑任务或脏目录时不覆盖文件。网络获取可先进入 supervisor 暂存区，但暴露给模型的目录不能部分切换。

任务开始只检查 Wiki 是否就绪、资格/版本是否合适，不因新任务而重新复制。无需同步的任务直接复用常驻目录。

### 3.3 游标和投影恢复

断线重连先核对待确认的草稿/发布命令，再追赶正式变化。若游标已超出日志保留范围、epoch/projection 改变或文件校验失败，重新取快照；不是用不完整的事件序列猜当前文件。

ChangeSet 是事务单位。分页不能把一个批次应用到一半便推进游标；大内容可分块传输，仍需等完整批次校验完成。作用域过滤要保留序号进度：某批次没有本副本可见变更也能推进到已处理的序号，不能误判日志缺失。

## 4. Pod 内读写协调

### 读

多个只读任务可共同持有读租约；租约覆盖需要稳定 Wiki 的整个任务/回合。期间不编辑也不刷新 `/wiki`，所以多次文件访问看到同一正式文件版本。

worker 对 Wiki 必须有真实的只读文件权限；只禁名为 write 的工具不够，bash 也能改文件。临时计算目录可另行允许写入，但不复制 Wiki。

### 写与刷新

编辑者、目录刷新器使用同一排他准入。编辑独占包括 LLM 推理和草稿保存时间，这是用户接受的单目录取舍；它不持有远端数据库事务，不阻塞 Quoin 网页编辑。

读任务需要改 Wiki 时退出读阶段、派生编辑任务重新确认基准；不让多个读者持锁等升级。待同步/编辑时控制新读者进入，避免饥饿。

### 异常退出

编辑失败后先停止所有仍能写目录的子进程，核对 Quoin 草稿并恢复干净正式内容，再释放目录。不能仅解除锁，让新读者看到失败编辑的一半。

## 5. 上行：逐轮草稿确认

```text
标准文件工具完成一轮 Wiki 修改
  → supervisor 核对稳定变更及原始 manifest
  → SaveDraft(editId, sequence, commandId, changes)
  → Quoin 校验身份/序号/路径，事务保存修订、草稿指针、审计
  → COMMIT
  → 返回 durable draft receipt
  → 工具结果才报告“本轮编辑已保存草稿”
```

- 编辑任务每轮工具结束检查实际变更；不靠命令字符串猜 bash 有没有写文件。没有变化不保存新草稿。
- 一轮是可核对的操作批次，不是每个 OS write syscall。工具结束后仍持续写 Wiki 的后台进程必须收束，不能在文件继续变动时声称已完整捕获。
- 基准 manifest 在监督进程/Quoin 内，模型改一份本地 manifest 不能伪造基准或扩大删除范围。
- 草稿只引用改变的文档修订，不存一份全库快照；不进入正式变化 feed，不要求人工审批。
- 相同序号/命令重试返回原确认，同键异内容、序号倒退拒绝。
- 已保存但确认丢失，查询原命令即可。网络不可用时保留 OfflineDirty，不能报安全保存并继续污染共享目录。

**Pod 被销毁时，已获 Quoin 确认的草稿可恢复；尚未执行完成或尚未确认的最后一轮不承诺无损。** 数据库使用现有 WAL/FULL 配置，确认基于真实事务提交而不是先发成功消息再异步保存。

### 5.1 edit/write 怎样变成数据库修订

同步钩子在 `工具执行完成 → 工具结果返回模型` 之间，由 supervisor 执行：

1. **实际写文件**：如模型用 write 将 `/wiki/runbooks/mysql.md` 改好。未来若增加 edit 工具，同样先在文件上完成修改，不让模型直接写 SQL。
2. **确定变更**：write/edit 已知目标路径；bash 的候选路径可由文件监听加速发现，但最终必须与 supervisor 持有的基准/草稿 manifest 核对，不能只相信监听事件。读取实际文件字节，检查文件类型、UTF-8、大小、路径与内容 hash。
3. **生成检查点**：包含 editId、toolCallId、draftSequence、旧文档定位及实际新增/修改/删除内容。被删除的路径必须原来就在该副本的有效清单中；模型不能修改一份清单来伪造删除或引用。
4. **回传并原子封存**：经既有认证运行通道扩展内部消息。Quoin 在同一事务保存不可变草稿修订、推进草稿指针、封存该工具结果与审计/幂等记录；不存在先返回工具成功、再后台补写草稿的窗口。
5. **确认给模型**：COMMIT 后返回草稿收据，Plinth 更新本地草稿映射，再把工具结果交给模型。未收到确认时不报安全保存；用同一操作身份重试/核对。

这里的 SaveDraft 是基础设施接口，不是新增的模型工具。当前项目有 write、没有独立 edit；已安装的 Eino v0.9.13 实际提供 edit_file，但本项目尚未接入。对接该通用编辑能力时应接同一同步钩子。现有 `LocalToolCompleted → commitLocalTool → CompleteToolCall` 链路可以扩展，但**现行实现尚未同步 Wiki 文件**。

示例请求（表示语义，具体 wire schema 尚待冻结）：

```json
{
  "editId": "edit-42",
  "toolCallId": "tool-301",
  "draftSequence": 3,
  "changes": [{
    "op": "upsert",
    "documentId": "doc-18",
    "path": "runbooks/mysql.md",
    "baseRevision": "rev-12",
    "content": "# MySQL 排查\n...实际文件内容..."
  }]
}
```

保存草稿检查的是该编辑的前一草稿序号和身份。若 Quoin 正式文档已从 rev-12 变成 rev-13，仍可保全这份基于旧版本的合法草稿，并标明基准已变化；不能为了拒绝过时发布而连草稿都丢掉。**正式覆盖当前文档的版本校验在 Publish 做**。

在回传期间，本地编辑独占保持；需要稳定捕获文件，不能让后台子进程一边写，一边上传一个无法归属任何时点的正文。网络错误时保留未确认标记并暂停，避免下一轮覆盖尚未确认的差异。

### 5.2 双向分别同步什么

| 方向 | 内容 | 何时生效 |
|---|---|---|
| Plinth → Quoin | 新/改/删的草稿修订 | 每轮工具修改后持久确认，尚不公开 |
| Quoin → Plinth | 正式发布的变更批次 | 目录干净且获得排他刷新窗口后应用 |
| 编辑结束 → Quoin | 发布最新已确认草稿的命令 | 同一事务更新当前版本、变化 feed 和任务结果 |

例如 write 保存为草稿 rev-15，当前正式版本仍是 rev-12；自动 Publish 成功后，正式指针改为 rev-15 并生成一个 publishedSeq。Plinth 已有相同字节时可只核对 hash 并更新版本映射，不必再次下载正文；批次中的其他目录/关联文档变化仍要完整应用。

## 6. 正式发布与并发

编辑结束后，Publish 在 Quoin 一个事务内：

1. 复核身份、任务围栏、权限、来源有效性。
2. 对写集校验 expected document revisions，对读取依赖/任务范围做必要复核；新建/改名检查唯一性。
3. 引用已保存修订，一起更新所有文档当前指针/墓碑。
4. 追加 ChangeSet/ChangeItems、推进 publishedSeq、封存命令结果/审计及任务结果定位。
5. COMMIT 后返回发布确认，通知副本。

没有跨 Git/SQL 的事务窗口。同一事务也让草稿、任务终态和权威结果可一致裁决，但事务中不得调用 LLM 或传输大文件。

不同文档且依赖未冲突的编辑可先后成功；同页旧版本竞争不会最后写入者覆盖。标准 shell 不能精确证明读集时，使用保守的范围版本校验，不谎称拥有精确语义合并能力。

### 冲突恢复

Quoin 保留草稿与冲突信息；Plinth 停止旧编辑，在确认保全后更新正式副本，派新的编辑任务读取双方差异并重新应用。无需逐次人审批；证据矛盾确实无从裁决时可以记录未解决状态，不强行取一方。

正式发布确认后，副本在独占窗口应用对应变化并校验清洁，再恢复读者准入。没有变更的任务不制造发布批次。

## 7. 故障矩阵

| 事件 | 处理 |
|---|---|
| 更新通知丢失 | 游标拉取/定期序号核对补齐 |
| 草稿/发布确认帧丢失 | 按原命令 ID 查询，不重复修订或发布 |
| 同步批次只写了一半 | 不推进 appliedSeq，不开放读取；重试或重取快照 |
| 编辑时 Quoin 有人改同页 | 发布冲突，草稿保全，模型重新整理 |
| 副本失联且有未确认编辑 | 不同步覆盖、不伪造成功；先核对草稿再追赶 |
| 同 Pod 容器重启 | emptyDir 可能保留，但不能假定干净；核对后恢复 |
| Pod 重建 | 新取正式快照，再恢复 Quoin 已确认草稿 |
| 来源撤回/权限改变 | Quoin 拒绝相关后续调用/发布，必要时中断并重建任务；不能撤回模型已看过的字节 |
| 权威备份回滚 | 更换同步 epoch，旧游标/任务不得误用于新历史 |

副本状态建议为 Bootstrapping、Ready/Reading、Editing、SavingDraft、Publishing、Updating、Conflict、Disconnected/OfflineDirty。界面和指标显示 authoritySeq/appliedSeq、落后时间、编辑者、读者数与最近确认，不把连接在线当成版本最新。

## 8. 为什么不是 CouchDB 复制、git-sync 或双向 rsync

目前只有一个 Quoin 权威与一个常驻文件副本，不需要多主合并数据库。直接复制 SQLite 文件/WAL 也不是安全的在线文件投影机制。

git-sync 面向单向仓库发布，双向 rsync 面向字节同步；它们不决定 Quoin 的草稿持久性、任务权限、跨页事务或冲突。替换为数据库后保留的只是必要的文件投影适配器，不再叠加一套 Git 存储和发布协议。

## 9. 必测行为

1. 一个 Pod 一次引导，多任务复用 `/wiki`；无新版本时不传正文。
2. 读并行、写/刷新独占，读任务不混版本，不读到其他任务未发布草稿。
3. 草稿确认后立即删除 Pod，编辑仍在 Quoin；丢确认重试不重复。
4. 不同文档编辑可成功，同页/依赖冲突不丢写；多页发布全成或全不成。
5. 同步分页、漏通知、过期游标、断线和半批次故障都可恢复。
6. shell/子进程不能绕过副本权限或在释放编辑租约后继续写。
7. 权威与副本内容相同的宣称由实际 manifest/hash 校验支撑，不仅比较一个序号。
8. 改名/删除/恢复与权限变化有完整批次；未下发路径不被误删。
9. 备份恢复 epoch 不混旧新历史，所有内容仍由唯一权威修订记录拥有。
